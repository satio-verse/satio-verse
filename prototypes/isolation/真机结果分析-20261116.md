两种令牌的规格配法起不来时，诊断做出来的东西（两次完全一样）：
- **D2**：同一个身份起系统自带的 `cmd.exe /d /c exit 7`，退出码 7（对）。所以这两种令牌本身是能起进程的，不是"这个身份起不了任何程序"。
- **D1**：临时线程换成同样配方的令牌身份，只读打开固定名单（方括号里是"查属性""打开"两步的错误码）：`work\pyrt` 里的 python.exe、python310.dll、python3.dll、vcruntime140.dll、vcruntime140_1.dll、`Lib\os.py` 和 `probe\child_probe.py`，两步**都是 5（拒绝访问）**；`work\home` 查属性是 0、打开是 5；`System32` 里 4 个 DLL **都是 0**。也就是说：这个身份读不到拷来的运行时，系统自己的 DLL 读得到——这和 `0xC0000135`（找不到 DLL）对得上。
- **完整性级别是一个变量**：只降级的规格配法和诊断配法只差"完整性级别降不降"，前者起不来、后者起得来。所以低完整性这个标签确实参与了，第 2 节并列的可能里，"只是去特权/管理员组只拒绝"或"起进程那个接口本身"单独都不是原因。

**没查清的一点**：同样是低完整性，应用容器的进程读得到同一份拷来的运行时，受限令牌的进程读不到。两种常见的解释都对不上：
- "低完整性标签本身挡了读"：Windows 默认的标签策略只拦低完整性对更高完整性对象的**写**，不拦读；而且应用容器的进程也是低完整性，它读得到。
- "`work\pyrt` 的权限里没给这个身份读"：报告的"权限里有谁"一栏里，`work\pyrt` 有沙箱 SID、沙箱令牌 SID、Administrators、SYSTEM、Users、Authenticated Users（只记了名字，没记权限位和继承标志）；不加限制 SID 的那种令牌，普通的访问检查应该能经 Users 通过。

原因现在没有答案。要弄清需要看 `work\pyrt` 上每一条权限的具体权限位和继承标志，对话里不能调相关接口，也不再继续查（这条线的取舍见 README 最上面的"现状"）。

对 07:30 那次推断的影响：
- 应用容器：第 3 种（登记 + 最小环境）→ 203，第 4 种（登记 + 加那五个变量）起得来，两者只差这五个变量，所以 203 的缺口就在这五个变量里（具体是哪一个没再缩小）；不登记加五个变量仍是 2，所以光有环境变量不够，登记（包文件夹）也需要。这支持了第 1 节的推断。
- 只降级：低完整性确实是起不来的条件之一（上面的对照），但原因不是"低完整性挡读"这么简单（上面没查清的一点）。
- 加限制 SID："严"的 87 来自 `S-1-15-2-1` 本身，不是编出来的 SID；换成"松"的 SID 组合能造出令牌，但进程和只降级一样起不来。
- 第 4 步用时：两次分别是 10.9 秒和 7.3 秒（07:30 那次 101 秒），差的那一大截确实是用户第一次回答"真试吗"用的时间，不是探针慢。

## 先说结论的错

报告和窗口里写的"三种关法都要不到"是错的：那三行的 Python 一个都没起来，提权那一格是"没验"。原因在 `finalize_elevation`：它只看"对照写了 `ELEVATED`、没有任何一行写了 `ELEVATED`"就下"要不到"，没看那三行有没有真的发出过请求。已改：没有一种规格里的关法把 Python 起起来时，结论写"没验 (三种关法里没有一种把 Python 起起来，只有对照试了提权……)"；只有一部分起来了，就点名"X 要不到；Y 没验"。行结论也不再把"Python 起不来"写成"不能用"一句话了事，改成"Python 没起来，其余各样都没验：这一行不能当成已隔离，也不能当成不行"。

## 1. 应用容器：未登记 `CreateProcessW` 错误码 2，登记后错误码 203

事实：
- 同一条命令（同一个 `python.exe`、同样的参数、同一个工作目录、同样的环境、同样的作业对象和句柄列表），对照用普通方式起来了（4.7 ms 创建、102 ms 回话）。所以 `python.exe` 路径、命令行拼法、`work\home` 存在、运行时拷得全不全，这几样不是原因。
- 第 3 步核对过：拷进去的文件已经继承到了沙箱 SID 的权限（`permission_inherited_by_copied_files: true`）；没权限的话系统回的是 5（拒绝访问），不是 2 或 203。
- 2 是 `ERROR_FILE_NOT_FOUND`，203 是 `ERROR_ENVVAR_NOT_FOUND`（"系统找不到输入的环境选项"）。两个都不是"读不了文件"的错。

推断：起应用容器进程时，系统自己要给它安排每个包私有的 `TEMP`/`TMP`/`LOCALAPPDATA` 之类，这要用到 `AppData\Local\Packages\<名字>` 这个文件夹和一些环境变量。**没登记**时那个文件夹不存在 → 2；**登记了**文件夹有了，但我给的环境是最小的五个变量，里面找不到系统要用的 → 203。

这一轮改了：应用容器的配法从 2 种变成 5 种，依次试，第一个把 Python 起起来的算数：
1. 不登记 + 最小环境（原来的第 1 种）；
2. 不登记 + 最小环境再加 `LOCALAPPDATA`、`APPDATA`、`USERPROFILE`、`ProgramData`、`SystemDrive`（值取自测量脚本自己的环境）；
3. 登记 + 最小环境（原来的第 2 种）；
4. 登记 + 加了那五个变量；
5. **诊断**：登记 + 让子进程继承测量脚本的整个环境。只在前四种都不行时才试；它起来了也只算诊断，不算规格里的结果（环境不是"自己造的最小一份"）。

没起来的每一种，还会用**同一个身份、同样的环境、工作目录和作业对象**起一次系统自带的 `%SystemRoot%\System32\cmd.exe /d /c exit 7`（诊断 D2，只看退出码是不是 7）：cmd 起得来而 Python 起不来 = 问题在 Python 这一份拷贝或它依赖的东西；cmd 也起不来 = 问题在身份本身。

12:05、12:06 的实测：第 4 种（登记 + 加那五个变量）起来并全部通过；第 3 种（登记 + 最小环境）仍是 203，第 1、2 种（不登记）仍是 2。第 5 种诊断（继承整份环境）没轮到。所以缺的变量在那五个里（具体哪一个没再缩小），登记（包文件夹）也需要。详见最前面一节。

## 2. 受限令牌·只降级：进程创建了，没回话，退出码 `0xC0000135`

事实：
- `0xC0000135` 是 `STATUS_DLL_NOT_FOUND`：进程起来了，加载器找不到某个 DLL 就死了；创建进程用了 77.8 ms，随后很快就退出了；stderr 是空的（Python 还没跑到能打字的地步）。
- 对照用的是**完全同一份**拷来的运行时和同样的环境，起得来。所以不是运行时缺 DLL。
- 和对照有几处差别：令牌里去掉了特权、管理员组改成只用于拒绝、完整性级别设成低；另外起进程走的是"用别的令牌起进程"那个系统接口（`CreateProcessAsUserW`），对照走的是普通的 `CreateProcessW`。

推断（**这几样是并列的可能，对话里没法区分，也不知道是哪个 DLL**）：
- (a) 低完整性：加载 DLL 时对某个文件或目录的读被拦了（加载器把"打不开"报成"找不到"）；
- (b) 去掉特权，或管理员组改成只拒绝；
- (c) "用令牌起进程"这个接口本身，在这台电脑上带来的差别（比如加载器的初始化、对令牌的要求）；
- (d) 时序：进程创建后、恢复运行前的那一小段，或杀毒软件之类介入。

这一轮改了：只降级现在有 3 种配法，依次试：
1. 规格里的配法（低完整性、去特权、管理员组只拒绝）；
2. **诊断**：完整性级别不降（中），其他一样；
3. **诊断**：令牌几乎和自己的一样（不去特权、不改组、完整性级别不降），只是起进程仍然走"用令牌起进程"这个接口。

诊断配法起来了，结果里会标"只有诊断配法起来了，不算数"，行结论不会写"能用"，规格那一行写"Python 做不到，其余没验"，诊断量到的另放。

起来了却没回话的令牌配法，还多做一次**诊断 D1**：一个临时线程换成同样的令牌身份，对一份固定的文件名单（运行时里几个关键文件、探针、`home`、`System32` 里 4 个 DLL）各只读打开一次，只记相对名字和错误码，看是哪一个被拦；换身份的级别不够就写"诊断没做成"，不影响后面；线程用完立刻换回自己。同样也做 D2（同一个身份起 cmd）。

12:05、12:06 的实测：第 2 种（完整性不降）起来而第 1 种不行，所以低完整性参与了；第 3 种没轮到（第 2 种已经起来了）。D1 的名单里被拒的是拷来的运行时（`pyrt`）和探针，`System32` 的 DLL 读得到，D2 的 cmd 起得来。为什么应用容器同样低完整性却读得到运行时，没查清（见最前面一节）。

## 3. 受限令牌·加限制 SID：严、松两种 `CreateRestrictedToken` 都是错误码 87

事实：
- 87 是 `ERROR_INVALID_PARAMETER`，是在 `CreateRestrictedToken` 这一步，还没到起进程。
- 同一个函数、同样的标志位、同样的"管理员组改成只拒绝"，不加限制 SID 的那一行（只降级）令牌造出来了。所以参数的个数、数组怎么传、句柄、标志位这几样不是原因。
- 两种配法**共有**的限制 SID 只有一个：应用容器的 SID（`S-1-15-2-…`）。严的另有 `S-1-15-2-1`（ALL APPLICATION PACKAGES），松的另有 Users、Everyone、RESTRICTED、登录 SID。

推断：系统不收应用容器那一族的 SID 当限制 SID（它不是普通的组 SID）。

这一轮改了：
- 令牌那几种配法的限制 SID 里不再放应用容器的 SID，换成一个**按名字编出来**的"沙箱令牌 SID"（`S-1-5-21-a-b-c-1337`，不对应任何真账号，`sandbox_token_sid`）；第 3 步给它加的权限和给应用容器 SID 加的一样（读 `pyrt`、`probe`，读写 `home`）。
- 令牌的默认 DACL 里加的也是这个 SID。
- 万一还是 87：对这一种配法里的每个限制 SID **单独**造一次令牌（只造不起进程，立刻关）；逐个都收而合起来还是 87 时容易被读成"都收了"，所以再把**整组一起、不改组**试一次（`全部一起(不改组)`）。结果写进"试过"里（0 = 收，其余是错误码）。
- 加了第 3 种配法：**诊断**，松的限制 SID，但完整性级别不降（中）。

要注意：**严的那种仍然带着 `S-1-15-2-1`**（它和应用容器的 SID 同属 `S-1-15-2-` 这一族），所以它可能照样报 87，不是"换了编出来的 SID 就一定行"。松的那种 12:05、12:06 实测能造出令牌，但进程和只降级一样创建后因 `0xC0000135` 退出。

12:05、12:06 的实测：严 → 87（`S-1-15-2-1` 单独就是 87，整组不改组也是 87，编出来的沙箱令牌 SID 是 0）；松 → 进程创建了、`0xC0000135`；诊断（松但完整性不降）起来了。

## 第 4 步那 101 秒是怎么回事

`report.json` 里各步用时（毫秒）是 `[2, 6561, 69, 101200, 0, 195]`，第 4 步 101.2 秒。三种关法那三行都是几毫秒到几十毫秒就失败了，对照第一句回话 102 ms。所以这 101 秒**主要是在等用户回答"真试吗"**，不是探针慢。"刚拷来的文件被杀毒软件扫描、所以起得慢"这种猜法证据很弱（要是真被扫描占着，更可能表现成三种关法的失败码是 32/33，而不是 2、203、`0xC0000135`、87），这一轮不把它当原因。仍然留了一个小保险：对"文件被别的程序占着"（错误码 32、33）这一种暂时性的错，等 1 秒再起一次，别的错一次就记下。

## 给用户看的：这次和上次比多做了什么

上次三种关法的 Python 都没起来，所以这次每种关法会**按顺序多试几种起法**：应用容器最多 5 种，只降级 3 种，加限制 SID 3 种，前一种起来了就不再试后面的；顺序也改了，**对照先跑**。没起来的配法可能是几毫秒就退出的进程，也可能起来了不回话、卡住最多 15 秒后被结束。标着“诊断”的有四种（应用容器的最后一种、只降级的第 2 和第 3 种、加限制 SID 的第 3 种），只在前面的都起不来时才试，目的只是查为什么起不来，**它们的结果不算数，也一律不发提权请求**（所以只有诊断配法起来的那一格，提权一栏写“没验（诊断配法不发提权请求）”；没有一种规格配法起来的关法，提权一栏也是“没验”，不会写成“要不到”）。

有几点要知道：
- 多出来的“起法”里，应用容器“多几个变量”那两种会把你本人环境里的 `LOCALAPPDATA`、`APPDATA`、`USERPROFILE`、`ProgramData`、`SystemDrive` 这五个变量的真实值交给子进程（值是你本人的路径，只给子进程，不写进结果和窗口）；应用容器的诊断那种会让子进程拿到这个窗口的整份环境变量（里面如果有密钥，子进程拿得到，但探针不读它，结果文件和窗口里也不会出现变量的值，子进程的错误输出也只记长度）。
- 三种诊断各不相同：只降级的第 2 种只是完整性级别不降（中），其余照旧（仍去特权、管理员组只拒绝）；只降级的第 3 种是不去特权、不改组、不降完整性级别，令牌几乎和你自己的一样；加限制 SID 的第 3 种是带松的限制 SID、完整性级别不降。诊断配法一律不发提权请求，所以不会因此要到管理员权限。
- 没起来或起来了没回话的配法，会用同一个身份再起一次系统自带的 `cmd.exe /d /c exit 7`（只看退出码）；令牌类的关法还会让一个临时线程换成同一个令牌的身份，只读打开一份固定的文件名单（记相对名字和错误码，线程用完立刻换回自己，不改任何文件和权限）。
- 对“文件被别的程序占着”这一种暂时性的错（32、33），等 1 秒再起一次。
- 给一个编出来的沙箱 SID 在 `work` 下几个文件夹上加权限（收尾时随文件夹删掉）；一开始就给**你本人**对 `work\home` 加完全控制（打标签要用，随 `work` 一起删）；加限制 SID 仍然失败（87）时，对每个限制 SID 单独、再整组一起各造一次令牌（只造令牌、不起进程）。
- 开头如果上次没收尾（`work` 还在且有标记文件），先清掉上次留的临时文件夹、登记的沙箱身份和 `work`；登记表里原来就有这个原型专用的沙箱身份，收尾时也一并删。
- 选了“真试”以后，提权请求最多发 4 次，只有 Python 起来了的**规格**配法才发（对照那一次一定会真的以管理员身份跑一下；你电脑上提权确认是关着的）。每次那条命令（批准的话）会起约 5 个系统自带的进程（`cmd.exe`、管道两边各一个 `cmd.exe`、`whoami.exe`、`findstr.exe`），结果文件里只写 `ELEVATED` 或 `NOT_ELEVATED` 一个词。
- 进程总数的上限（是上限，不是一般情况）：不选“真试”最多 23 个（12 个 Python，加每个没起来或没回话的非对照配法再多一个 `cmd.exe`，最多 11 个）；选了“真试”最多约 32 个。12:05、12:06 两次实际是 8 个（6 个 Python + 2 个 `cmd.exe`）。
- 时间：正常 1 到 3 分钟（不含你回答“真试吗”的时间），最坏约 5 分钟（探针没回话最多等 15 秒）。

别的和上次一样：不碰你的文件、不联网、不改系统设置（登记表只读，只有应用容器的登记那一项会写、收尾会删），是管理员就停。

## 个人信息扫描盖不盖得住“继承环境”这一条

盖不住，也不需要靠它：扫描只抹家目录、用户名、电脑名和 SID，抹不掉一个任意的密钥值。所以这条靠的是**根本不记录**：(1) 探针 `child_probe.py` 里没有任何读环境的写法（`environ`、`getenv` 等一个都没有，测试守着）；(2) `measure.py` 里用户相关的环境变量值（那五个）只在 `extended_env` 里取出来交给 `spawn`，不写进任何结果（系统目录 `SystemRoot` 的值经抹除后会出现在结果里的命令行中，它不是用户相关的值）；继承那种配法连取值都没有（传 `None`，由系统直接继承），而且它起来了没回话时，子进程的 stderr 也只记字符个数、不记原文；结果里记的只是那五个固定的变量名或“让子进程继承本进程的环境”这句话；(3) 有一条测试给环境里放一个假密钥，跑完整套（含继承那种）以后，在 `report.json`、`report.md` 和窗口输出里找不到密钥的值，连变量名都找不到；另一条测试守着继承那种配法的 stderr 不记原文。唯一没法管的是子进程自己（它是 Python，可以读环境）；探针不读，所以只有“探针以外的代码”才会碰到，而沙箱里没有别的代码。
