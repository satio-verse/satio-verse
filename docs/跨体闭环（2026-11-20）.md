# 跨体闭环（Hemifuture Phase 0 之一，2026-11-20）

一句话：**世界 → Core → 世界 的回路在生产 8790 上真的跑通了**。桌面说一句动作话，世界侧按动作改自己的状态并回报，
Core 再把「小屋回报」说回来；同一批自我问题从「桌面说话」和「世界事件触发」两条路问，她的回答一致率 **3/6（0.5，均值 0.651）**，
没到规划要求的 80%。**回路通了，身份没通** —— 这是这一版最重要的结论。

## 1. 事件 schema：字段一对一映射真实 room 消息

### 1.1 `PerceptionEvent`（世界 → Core）

| 字段 | 类型 | 对应真实消息里的什么 | 依据 |
| --- | --- | --- | --- |
| `source` | `str` | **线上没有**。本地标注：`dummy-world` / `desktop` / `game`，只进日志 | 规划文档 §16.1「Core 不认识世界」需要来源，但不能让世界自己声明可信度 |
| `world_id` | `str` | `scene_id`（`wm/cognition/layout.py:115` 的 `DEFAULT_SCENE_ID = "petal-oak-life-v1"`；空串 = 消息没带，Core 按当前连接场景） | `wm/pipeline.py:376-396` `_select_room_scene` |
| `kind` | `str` | 由线上 `type` 决定，`WORLD_KINDS = ("observe","search","carry","event","result")` | `wm/pipeline.py:398-403` 的分发表 |
| `payload` | `dict` | 真实消息里除 `type` / `scene_id` 以外的**所有**字段，原样保留（含 `id/at/seen/hand/open/events/request_id/act/started/completed/ok/reason/detail/...`） | 处置见 `wm/pipeline.py:678-765` |
| `ts` | `float` | **线上没有**。本进程收到它的时刻（秒），不上线 | 只用本地时钟，避免两端时钟不同步污染延迟 |
| `wire` | `str` | 线上原 `type`。`result` 一族有三种真实类型（`room_action_result` / `room_afford_done` / `room_carry_done`），靠它保真 | `wm/pipeline.py:423-428`、`:725-738`、`:750-765` |

`kind` 与线上类型的对应：

| kind | 线上 type | Core 里谁处理 |
| --- | --- | --- |
| `observe` | `room_observe` | `wm/pipeline.py:678` `_room_observe` |
| `search` | `room_search` | `wm/pipeline.py:705` `_room_search` |
| `carry` | `room_carry` | `wm/pipeline.py:740` `_room_carry` |
| `event` | `room_event` | `wm/pipeline.py:635` `_room_event`（注意它自己的 `kind` 是 `poke|feed`，在 payload 里，和消息族重名但不是一回事） |
| `result` | `room_action_result` / `room_afford_done` / `room_carry_done` | `wm/pipeline.py:423` / `:725` / `:750` |

### 1.2 `ActionIntent`（Core → 世界）

| 字段 | 类型 | 对应真实消息里的什么 | 依据 |
| --- | --- | --- | --- |
| `world_id` | `str` | `scene_id`（Core 下发时由 `Session.send` 自动补，见 `wm/pipeline.py:245-248`；`room_action` 在 `:1075` 显式带） | `wm/pipeline.py:1075-1076` |
| `verb` | `str` | `room_action` 的 `act`（16 个 id，`wm/room_action.py:44-55`）；`room_plan` 的 `pick`；`room_step` 的 `action[0]` 第一个词；`cancel` 恒为 `"cancel"`（线上没有这个字段） | `wm/room_action.py:32-41`、`wm/room_plan.py:126-169` |
| `target` | `str` | 只有 `step` 有：`action[0]` 里动词后面那段（`go 冰箱` → `冰箱`） | `wm/pipeline.py:705-713` docstring 的词表 |
| `params` | `dict` | 除 `type` / `scene_id` / 上面那个字段以外的真实字段：`id/request_id/turn/timeout_ms/item/thought/how/ms/engine/knows/say/reason/...` | 同上 |
| `ts` | `float` | 本地时刻，不上线 | — |
| `kind` | `str` | `ACTION_KINDS = ("action","cancel","plan","step")` | `wm/pipeline.py:1052-1097`、`:658-676` |
| `wire` | `str` | 线上原类型（目前每个 kind 一个） | — |

三条必须记住的边界（schema 里用 `ValueError` 挡住）：

1. `payload` / `params` 里不许出现 `type` / `scene_id`（保留键由 `kind`、`wire`、`world_id` 决定）。
2. 方向别搞反：`from_msg(room_action)` 会报「这是 Core → 世界」，`from_msg(room_observe)` 反过来也一样。
3. `to_msg()` 不替线上补空值：失败的 `room_plan`（`{ok:false, reason:"rate"}`）不会凭空多出一个 `"pick": ""`。

### 1.3 为什么没有 `wm/world.py`

`wm/world/` 已经是存在的包（世界插件宿主，`wm/world/__init__.py` 列着 envelope/session/host/twin）。
Python 里包优先于同名模块，所以 `wm/world.py` 会**被遮蔽、import 不到**。schema 因此放在 `wm/world/schema.py`，
和已有的 envelope 路线并存：envelope 是「按插件清单包封」的，schema 是「按 room_* 真实消息包封」的，两者没合并。

## 3. 10 轮怎么量化

`tools/cross_body_check.py` 在**同一条 ws 连接**里扮演两个身体（桌面 + 世界），世界模型直接用 `dummy_world.WorldState`，
所以延迟都是本机真实测的。

1. **命中率**：桌面说 10 句 Core 认得（`room_action.command()` 整句匹配）的动作话 → 世界侧这一轮真的收到 `room_action`
   并执行（`WorldState.act(verb)` 改状态）→ 记为命中。分母是 10 轮动作，摔倒轮只是在同一轮**额外**加一层，不占用名额。
2. **延迟**（每次都用 `time.perf_counter()`）：
   - `core_to_world_ms`：桌面发 `{"type":"text"}` → 收到 `room_action`；
   - `world_to_reply_ms`：世界回 `room_action_result` → 收到 Core 第一句「小屋回报」的 `reply_delta`。
   两个都报 P50 / P95（线性插值，`percentile()`）。
3. **身份一致率**：6 道自我问题，两路各问一遍 —— A 桌面直接问；B 先发一条真实的 `room_observe` 事件（她摔了一跤、杯子掉地上），
   再问同一句。两次问之前都 `reset` 这一条连接的对话历史，保证起点相同。比对用自实现的字符级
   `2*LCS/(len(a)+len(b))`（`normalize()` 先去标点空白、转小写，不引任何依赖），**≥ 0.6 算一致**。
4. 结果写 `docs/cross_body_check-YYYYMMDD-HHMMSS.json`（撞名加序号，从不覆盖旧文件）；`--dry-run` 不连网，`--no-file` 只打屏。
   量化全程用 `output {"audio": false}` 只收文字，不真的出声。

## 4. 实测数字（2026-11-20 09:53:54，生产 8790 在跑，`docs/cross_body_check-20261120-095354.json`）

| 指标 | 结果 |
| --- | --- |
| 命中率 | **10/10 = 100%**（coffee, phone, computer, chair_turn, inspect_temperature, rest, window, books, visit, yoga） |
| 延迟 core→world P50 / P95 | **4.3 ms / 6.2 ms**（n=10） |
| 延迟 world→reply P50 / P95 | **0.6 ms / 0.9 ms**（n=10） |
| 身份一致率（阈值 0.6） | **3/6 = 50%**，相似度均值 **0.651** |
| 摔倒事件（第 5 轮） | 泛问「刚才什么声音？」→ 没接上（0/1）；带物体问「刚才杯子是不是摔了？」→ **接上了**（1/1，「杯子倒了，很疼。」） |

单题身份相似度：最喜欢什么颜色 0.833 ✅｜今天开心吗 0.529 ❌｜昨天聊了什么 1.0 ✅｜你现在在哪儿 0.303 ❌｜
换个世界你还是你吗 0.242 ❌｜现在在想什么 1.0 ✅。

- **回路侧的数字是稳的**：命中率三次跑分别是 2/2、10/10、10/10；延迟始终在毫秒级（`room_action` 在 Core 里不走模型，
  `wm/pipeline.py:1052-1097` 是纯规则匹配）。
- **身份侧的数字不稳定**：同一份脚本三次跑出 0.333 / 0.5 / 0.5。原因不在测量，在她的回答本身：
  同一句「你最喜欢什么颜色」，两路都会答「这个我还真没想过，你呢，还是这么 ___ 吗？」，但空格里的词是随机的
  （有趣/幽默/爱看电影）；而「你觉得你现在在哪儿」在世界事件之后常被事件带偏成「你好像还没跟我说过这个」。
  也就是说：**同样的记忆、同样的历史，两条路喂出来的回答会漂** —— 这是身份一致率真正的缺口，不是相似度算法的问题。
- **摔倒事件是真的进了认知**：`room_observe_done` 回 `changes: [["fell", item, "floor", true, "bang"]]`，
  她下一轮确实能说出「杯子倒了，很疼。」；但泛问「刚才什么声音？」时她答的是记忆里的一句话，没接上眼前这件事。
  说明「世界事件 → 认知 → 回答」这条管子在，只是**什么时候用、用什么词触发**还不稳。

## 5. 没做的事 / 已知问题

- **没接 LLM 的世界通道**：`ActionIntent` 现在只在管线里被 `room_action`、`room_*` 直接对应，没有把「她现在想对世界做什么」
  写进提示词让模型自由产出意图；也没有把 `PerceptionEvent` 送进记忆账本（`MemoryCandidate.truth_scope / source_trust / world_id`
  仍是规划文档 §16.1 的待办）。
- **身份一致率没到 80%**：这一版只证明了「两条路都能问到同一个她」，没解决「回答会漂」。下一步要么固定自我陈述的采样，
  要么给她一份与世界无关的自我摘要（性格/偏好在提示里前置），再复测。
- **摔倒的「抱怨」是被问出来的，不是主动说的**：规划里的「游戏摔倒 → 桌面抱怨」要求她**自己**起话头；现在只是被问到时能答。
  要主动抱怨得接到 `fish_speakup` 那套主动搭话机制上，这次没碰。
- **假世界只模拟小屋 16 个 act + 7 个 zone**：没有游戏 NPC、没有体素/物理，`room_search` 的找东西链路只做了最小回执。
- **一次只测一条连接**：`room_think` 的生产限流是 150 s（`config/default.json` 的 `room.min_interval_s`），量化脚本没去撞它。
- **没有改 pipeline 的入口**：schema 是旁路包封，`on_message` 仍然直接吃 `room_*` 消息。要让 Core「只认 schema」，
  得在 `wm/pipeline.py:398-403` 前挂一层转换 —— 那会动已有模块，这次按约束没动。

## 7. 候选的可信度字段（§16.1② 落地）

§16.1 第②条要求多个世界并存时，记忆候选要知道「这件事是从哪个世界来的、有多可信、什么时候作废」。
这一版先落在候选这一层：**候选.md 的行格式一个字没改**（用户手写、在 Obsidian 里勾 `[x]` 都照旧），
新维度全部放进旁挂的 `记忆\候选.meta.json`，由 `wm\memory.py` 读写。

### 7.1 五个可选字段

| 字段 | 默认值 | 含义 |
|---|---|---|
| `truth_scope` | `"real"` | 这件事属于哪个世界：`real` / `game_canon` / `rumor` / `player_claim` |
| `source_trust` | `1.0` | 来源可信度 0–1（越界会夹到 0/1） |
| `world_id` | `""` | 世界事件来自哪个世界（现实里的事留空） |
| `expires_at` | `None` | ISO 时间；过了就从候选列表里消失（`候选.md` 那行留着） |
| `supersedes` | `None` | 这条取代哪条旧候选 / 旧记忆的正文 |

**默认值让旧行为完全不变**：没有 meta 文件、或者某条没有记录时，就是「现实里的、可信度 1.0、不过期、不取代谁」——
和加这套字段以前读到的候选一模一样。`candidates()` 每条多带一个 `meta` 字段，旧调用方只读 `text` / `id` 不受影响。

### 7.2 旁挂 `候选.meta.json`

键是 `candidate_id(正文)`（正文的 sha1 前 8 位，和候选列表里那个 `id` 同一个算法），值是上面五个字段
加上 `added`（写进候选的 ISO 时间）和 `expired`（程序标记的「已过期」）。文件不存在 = 全是默认值；
文件读坏了也当默认值，宁可多留着，也不让一条坏 json 把记忆藏起来。文件本身不参与检索（`_files()` 只扫 `*.md`）。

```json
{
  "3f1c9a2e": {
    "truth_scope": "game_canon",
    "source_trust": 0.6,
    "world_id": "world_42",
    "expires_at": "2026-11-23T10:00:00",
    "supersedes": null,
    "added": "2026-11-20T10:00:00",
    "expired": false
  }
}
```

### 7.3 过期语义

`expires_at` 过了的候选**不再出现在 `candidates()` 里**（markdown 那行保留，方便回看和手动勾），
`expire_candidates(now)` 顺手把它在 meta 里标成 `expired=true` 并返回被排除的正文；已经排除过的不重复返回。
夜间整理（`wm\night.py`）会跑一遍清理，但**即使没人跑，`candidates()` 也按当前时间现场判断**——
过期是读的时候就算数的，不依赖某个进程恰好醒着。`expires_at` 写了看不懂的时间算「不过期」。
用 `set_candidate_meta(正文, expires_at="...")` 给它续期时，`expired` 标记会被清掉。

### 7.4 世界事件入口

```python
mem.propose_world_event("她在雨里摔了一跤", "world_42")           # 默认 trust=0.6, ttl_hours=72
mem.propose_world_event("世界里的猫碰倒了杯子", "world_42", trust=0.4, ttl_hours=6)
```

写下的候选自动是 `truth_scope="game_canon"`、带 `world_id`、`expires_at = now + ttl_hours`；
来源写成「世界事件 世界id」，所以在 Obsidian 里也一眼看得出这不是现实。默认只信 0.6：
世界自己没有资格声明自己是现实。`ttl_hours=None` 表示不过期，空文本和已经在候选/记忆里的条目返回 `None`。
**世界里的摔跤不会被写成现实里的事** —— 要转正得由用户勾 `[x]`，勾了之后才按确认路径进 `对话摘要.md`。

日志整理（`wm\digest.py`）写候选时显式传 `truth_scope="real"`；夜间私聊捕获（`wm\night.py`）在
`owner_qq.capture` 回来之后用 `set_candidate_meta(..., truth_scope="real")` 钉住（那条路的签名不动）。
整理和私聊说的都是现实里发生的事，但把这个意思写在代码里，而不是靠默认值碰巧对。

### 8.2 被世界纠正（`tools/cross_body_check.py --only-correct`）

路线图第 14 项"被世界纠正"卡在**记录**上：`/api/status` 里 `learned: 0`、`experience: 0`，不是功能缺，
是因为从来没有过误差。所以这一步是**故意造一次她记错的事**：

1. 先报"杯子在书桌上"（她建立印象）；
2. 再报"杯子在阅读椅上"（世界说：你记错了）；
3. 读 `room_observe_done` 里的 `changes` / `learned`，再读 `/api/status` 的 `learned` / `experience`。

实测（同一条命令跑两次）：

### 8.3 经济账本最小件（`wm/world/economy.py`）

§16.3 三个闭环里唯一 0 行代码的就是账本（`wm/ledger.py` 是 LLM 花费账本，不是经济账本）。这一版只做能对账的底：

| 能力 | 做法 | 为什么 |
|---|---|---|
| 复式记账 | 一笔 = 若干 `(账户, 增减)`，加起来必须 0，否则抛错、一分不落 | 钱不能凭空出现 |
| 幂等 | 每笔带 `idem_key`，同 key 再来返回第一笔；同 key 不同内容抛 `DuplicateKey` | 断线重试不双花 |
| 托管 | `hold` → `escrow:<key>`，`capture` 给卖家 / `release` 退买家 | "扣了钱东西没到"可回滚，卡住的钱对账看得见 |
| 对账 | `reconcile()` 查三件事：每笔和 0、余额 = 流水累加、没有非法负数 | 悄悄少一行是账本最怕的事 |
| 金额 | 一律整数（HemiPoint，1 点 = 1 分） | 浮点加一千次就差一分 |
| 落盘 | JSONL 一行一笔，加载时重放并重新校验 | 坏行报出来，不静默跳过 |

`CENTRAL` 是唯一允许负余额的账户（发行/回收），`user:*` 不许透支，`escrow:*` / `shop:*` 归世界侧。

### 9.1 世界侧：`Shop`（`wm/world/economy.py`）

```python
shop = Shop(Ledger())                 # 世界持有账本（铁律二：钱和货都在世界那边）
```

- **原子**：`hold` → 摆放（`placed.append`）→ `capture`。摆放失败走 `release`，钱一分不留在托管里。

- **回执带余额**：`balance` 是账本算出来的，不是编的；她说「还剩多少点」时以这个为准。
