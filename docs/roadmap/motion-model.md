# 轻量动作生成模型：MB 级、浏览器里实时

2026-10-27 研究第一步（R0：只读资料、做规划、测基线，没有下载、没有训练、没有花钱）。同一天按用户转来的核查意见修了测法，重测了基线（第 3、4 节），改了许可表（第 2 节）和 R1 的设计（第 5 节）。

同一天下午做了 R1a（第 5 节"R1a 实际怎么做的"及之后几小节）：
- 试了三版加一个偏置旋钮，没有一版全部过门槛；
- 最好的是第二版加偏置 0.1：动作数据 52 → 2.6 MB，延迟和耗时都过，坐下、拿放和脚打滑还差；
- 没换进行动层，网页和桌宠还用原来的库。

缘起：用户看了 B 站 流明_Lumen_ 的视频 BV1DnnZ6iESP《仅需24MB内存！轻量化的ADRY实时AI动画方案!》（标题里的 ADRY 是 ARDY 的笔误），问能不能按这个思路做 MB 级内存的实时动作生成。
- 视频 61 秒，没有字幕，代码还没公开，"24 MB"没法核实。
- 作者就是 HAST-SEC 的作者（HAST-SEC 非商业，我们锁在 v0.1.1）。

为什么要做：现在比心、托腮这类新动作都是在 `web/locomotion.js` 的 `_emote` 里一个一个手写 IK、一个坑一个坑修出来的。用户要的是"说一句就生成"的动作模型。

## 0. 结论

| 问题 | 结论 |
|---|---|
| ARDY 大在哪 | 推测成立：文本编码器 LLM2Vec-Llama-3-8B 约 80 亿参数（bf16 约 14 GB 显存），占全部参数的约 98%。运动部分：去噪器 623 MB（fp32，约 1.56 亿参数）+ 分词器 142 MB（约 3500 万参数），合计约 765 MB。 |
| 去掉文本编码器就是 MB 级了吗 | 不是。运动部分 fp16 还有约 380 MB，要再缩 15–40 倍。 |
| 能缩的理由 | 我们的动作范围窄：一个角色、室内、二十几个技能（走、坐、拿放、手势、表情动作）加几种情绪步态。不需要开放的文本词表。 |
| 有没有先例 | 有，但任务都比"说一句就生成"窄。Learned Motion Matching：官方示例约 590 MB 的运动匹配库换成约 17 MB 网络，16 位量化后约 8.5 MB。CAMDM：风格化移动，20 MB 权重，RTX 3060 上八步推理约 13 ms。PFNN：10 MB，每帧 1.8 ms。 |
| 文本怎么办 | 交给已有的 0.8B 意图模型：它出结构化动作指令，指令换成一个几十维的嵌入。动作网络针对我们的结构化指令从头训（见 R2），不能拿 ARDY 的权重配一个小编码器。 |
| 第一个实验 | R1 第一步只做**中性风格的移动加待机**的压缩：把这两个库蒸馏成 LMM 式的小网络（手写 JS 推理），在同一套评估里 A/B。留不留看实测，再决定扩不扩到其他风格和手势。数据都在本机，不用下载。 |

## 1. 资料：哪些能借过来

### 1.1 ARDY（Zhao 等，NVIDIA / ETH，SIGGRAPH 2026，TOG 45(4) 86）

来源：论文 PDF（项目页 research.nvidia.com/labs/sil/projects/ardy）、仓库 github.com/nv-tlabs/ardy、Hugging Face 上 `nvidia/ARDY-Core-RP-20FPS-Horizon40` 的文件列表。

| 方面 | 做法和数字 |
|---|---|
| 混合表示 | 根显式：位置 3 维 + 朝向 cos/sin，共 5 维。身体用分词器压成潜变量。每 4 帧一个 token（patch 4），token = [4 帧的根, 身体潜变量]。 |
| 分词器 | 编码器、解码器各是 8 层因果 Transformer，宽 512。默认用 FSQ（64 档 × 128 维），比 VAE、普通自编码器训练稳定。解码器把全局根换成局部的根速度再还原身体。去掉这一步，脚滑 0.264 → 0.303 m/s。 |
| 两段去噪 | 每一步去噪先用"根 Transformer"预测干净的根，再用"身体 Transformer"以根为条件预测身体潜变量，两段交替。两个 Transformer 各 8 层、8 头、宽 1024，合计约 1.56 亿参数。 |
| 两段 vs 一段 | 有约束时，一段式全身关键帧误差 0.023 → 0.079 m、路点误差 0.024 → 0.164 m。 |
| 混合 vs 全显式 | 全显式表示：R-precision 65.5 → 53.9，路点误差 0.024 → 0.203 m。 |
| 约束 | 约束是一份带掩码的显式动作（根路点、根路径、全身关键帧、末端位置和朝向、脚触地），拼进输入 token。根约束直接覆盖带噪的根（overwrite）。超出生成窗口的远期目标也作为额外 token 喂进去，所以"10 秒后到门口"不用另训 RL 策略。 |
| 自回归 | 历史长度可变（0 到 8 秒），未来目标最多 10 秒。一次生成 C 个 token。训练时随机丢掉 10% 的文本和约束，用于无分类器引导。 |
| 中途换指令 | 换指令或换约束时马上重新规划。生成在后台进行，已经生成的 B 帧照常播放，同时当历史，所以慢的模型也不会卡画面（论文图 5 的"延迟感知重规划"）。 |
| 步数和窗口 | 默认 10 步；4 步仍可用，1–2 步明显变差。窗口 8 帧时约束和换指令反应更快，4 帧训练不稳。 |
| 速度 | RTX 4090：4 步一次 33 ms，10 步一次 63 ms，每次出 40 帧（20 fps 下 2 秒）。 |
| 数据和训练 | Bones Rigplay，专有数据，约 700 小时、31.5 万段。分词器单卡 A100 训 400 万步；去噪器 4 × A100 训 100 万步，batch 512。 |
| 文本 | LLM2Vec，基于 Llama-3-8B-Instruct。门控模型，要 HF token；bf16 约 14 GB 显存。 |
| 许可 | 代码 Apache-2.0。权重是 NVIDIA Open Model Agreement，我们不用。训练数据专有。 |

**借：**
- 根显式、身体用潜变量的混合表示，以及解码时局部化根。
- 两段式（先根后身体）。
- 约束写成带掩码的显式特征，根约束覆盖，远期目标作为额外 token。
- 变长历史和短窗口（8 帧）。
- 少步数（4 步）。
- 后台生成加重规划缓冲。
- 用 FSQ 当分词器。

**不借：**
- 8B 文本编码器。
- 权重和专有数据。
- SOMA、G1 骨架。

代码可以参考结构，但我们自己写，和 `web/mm.js` 的做法一样。

**注意：语义不会跟着维度对齐。** ARDY 的运动网络学的是 LLM2Vec 那个表示空间。换一个小编码器、把向量投到同样的维度，不等于语义也对上了。所以 ARDY 的权重即使许可允许也用不上；我们的动作网络要针对自己的结构化指令（技能、风格、目标、约束）从头训。

### 1.2 紧凑的实时动作网络

| 工作 | 是什么 | 大小、速度 | 借什么 | 许可 |
|---|---|---|---|---|
| PFNN（Holden 等，2017） | 网络权重随步态相位循环变化 | 每帧 1.8 ms / 10 MB；预先算好可以到 0.8 ms，但要 125 MB | 相位当条件。但我们的待机不是周期动作，暂时不用 | 论文 |
| **Learned Motion Matching**（Holden 等，2020） | 运动匹配拆成 4 个网络：压缩器（姿态 → 潜变量）、解压器（特征 + 潜变量 → 姿态）、步进器（预测下一帧的特征和潜变量）、投影器（查询 → 最近的特征和潜变量） | 官方示例约 590 MB → 约 17 MB，16 位量化后约 8.5 MB。参考实现的步进器是 2 层 512 宽的 ReLU MLP，训 50 万步，batch 32，窗口 20 帧 | **R1 照这个做**：我们已有同一套特征和惯性化（`web/mm.js`） | 代码 MIT；示例数据 LaFAN1 不能商用（我们不用它的数据） |
| Motion VAE（Ling 等，2020） | 自回归条件 VAE，解码器是专家混合；潜变量当强化学习的动作空间（走到目标、摇杆、沿路径、迷宫） | 预训练文件名 `posevae_c1_e6_l32`。按文件名推测：条件 1 帧、6 个专家、潜变量 32 维 | R2 的一步式对照组；以后专门电脑上做强化学习时的潜变量接口 | BSD-3 |
| DeepPhase（Starke 等，2022） | 周期自编码器学出多维相位流形，用它比距离比原始姿态更准 | — | R1 可选：相位当额外的匹配特征（对比加和不加） | 论文 / AI4Animation |
| **CAMDM**（Chen 等，SIGGRAPH 2024） | 风格化移动的自回归扩散 Transformer，条件是风格标签、未来根轨迹和过去 10 帧，生成未来 45 帧 | 20 MB 权重；RTX 3060 上跑 ONNX，八步推理约 13 ms（2/4 步 6/8 ms）；训练 1 × A100 约 20 小时；数据 100STYLE（400 多万帧、100 种风格） | **R2 的近邻对照**：数据可商用，任务（风格 + 轨迹）和我们的走路最像。它说明的是"20 MB 级扩散在风格化移动上够用"，不包括拿放、表情动作 | 代码 Apache-2.0（Unity 部分 GPL-3）；权重没写许可，不用 |

## 3. 任务和指标

**任务**：
- 输入：
  - 指令：R1 是风格和类别的独热，R2 起是指令嵌入。
  - 根目标：期望速度和朝向，或路径点，或终点加朝向。
  - 可选的末端约束：某个时刻手腕或脚的位置、朝向，带掩码。
  - 历史：上一段输出。
- 输出：VRM 标准骨架 22 根骨骼（和 `tools/build_motion_db.py` 的 `BONES` 一致）在 30 fps 下的下一帧：
  - 骨骼旋转（根朝向坐标系）；
  - 髋部位置；
  - 根运动；
  - 左右脚触地。
- 格式和 `mm.js` 的 `samplePose` 返回的一样，所以只换"动作来源"，后面的 IK、接触、平滑、落地各层都不动。

**指标**：沿用已有的，另外加几项。量法都在 `tools/motion_baseline.mjs` 里。

| 指标 | 怎么量 | 出处 |
|---|---|---|
| 痛觉各项（穿模、脚打滑、关节越界、重心、跳变、冲击、隔空拿放……） | 每个场景累计 | `web/pain.js`，`kin.end` |
| 像真人分 | 生成动作和动捕参照集的最近邻距离 / 留出真人的距离（1 ≈ 真人） | `web/motion-score.js` |
| 场景 | 待机、走、坐、拿放、手势、表情动作、说话，以及体检用的全套 | `web/motion-eval.js`，`tools/motion_eval.mjs`，`tools/motion_checkup.py` |
| **模型大小** | 文件字节数、参数量 | 新 |
| **运行内存** | 页面里动作数据或权重占的字节（ArrayBuffer 去重计数）。R1 起另外分开量：文件大小、载入后的运行时占用（16 位展开成 Float32、缓存、中间结果）、载入时的峰值 | 新 |
| **每帧耗时** | 真时钟，按层：动作来源、行动层、接触、平滑、痛觉、整帧 | 新 |
| **响应延迟** | 见下 | 新（`lat_*` 场景） |
| **走到目标的误差** | `reach:目标`：每个目标单独从出生点走，停下 0.5 秒后离站位多远、朝向差几度 | 新 |
| **脚滑** | 两种：痛觉 `slide`（锁定的支撑脚滑超过 5 mm 的部分）；以及不经过脚锁的量法（脚低于静止脚踝高度 + 2.5 cm 时的水平速度，同 ARDY；这个阈值把贴地摆动的脚也算进去了，只用来做相对比较） | 新 |
| **情绪风格的步态** | `walkstyle:情绪`：5 种情绪各走一遍 `walk` 的路线，确认风格库确实换上了 | 新 |
| 指令正确率（R2 起） | 用标注好的数据训一个小分类器判断"做的是不是那个动作"；或者在带标签的参照集里找最近邻 | R2 再定 |

**响应延迟怎么判**（第二版测法，2026-10-27 按核查意见改）：
- 所有阈值都从发令那一帧算起，按模拟时钟（60 fps，一帧 16.7 ms）。只算运动层自己，不含意图模型和网络。
- 每项先录 1–1.5 秒不发指令的对照；位移类阈值取"固定值"和"对照里最大值的 2 倍"中较大的一个。
- 挥手、比心不只看位移，还要看到动作本身的特征：
  - **挥手**：手腕抬出对照的晃动范围；手腕举过肩；举着时左右摆两个来回，每次 3 cm 以上。
  - **比心**：两手食指远端关节靠到 7 cm 以内（做满时 5–6 cm，待机时 14 cm）；两手腕在胸口以上、头以下，在胸口前方 15 cm 以外。待机时双手常交叠在腹前，只看手腕会误判。
- 超时、或者对照段（不发指令）就已经满足特征，场景记失败（`ok: false` 和原因）。
- **换目标、停下要等走稳**（2026-10-27 傍晚 R1a 时补的）。原来是速度一到 0.4 m/s 就录对照、发指令，这样有两个问题：
  - 边走边转向目标的动作来源，那一刻还在转弯，对照段的方向抖动有 160° 以上，阈值抬到够不着，记成"没测到转向"；
  - 原库起步走得直，那一刻碰巧是直的。

  现在要求速度连续 0.25 秒在 0.4 m/s 以上、方向变化不到 5°，3 秒内走不稳记失败。用新测法，原库的换目标是 233 ms（第二版基线写的 50 ms 作废），停下是 667 ms（原来 733 ms）。
- 延迟门槛改成和原库比：取几个种子里最慢的那个，不超过原库 × 1.2 再加一帧（17 ms）。原来的绝对门槛是照着有问题的基线数定的。

**每项独立复位**：
- 每个场景开始前 `runEval` 自己会复位。它没管的行动层状态（表情动作、交叠、仪态、情绪体态、风格层的权重），脚本在复位时另外放回页面刚载入时的样子。
- 延迟、走到目标都拆成一项一个场景，不连着测。

**版本固定**：
- 页面用到的代码（`web/**/*.js`）、动作库（`models/motion/*`）、形象、场景、脚本本身都记 SHA-256，跑前跑后各算一次。

**测的时候查到的**（都没改，记给动作会话）：
- `web/locomotion.js` 的 `setStyle` 会留下过时的"待换库"：情绪 A → 中性（站着时不搜索，中性库只挂着）→ 再换回 A 时，因为当前库就是 A，挂着的中性库没被清掉，第一次搜索就换成了中性。评估里连着跑风格场景时，种子 2 必现，脚本里绕开了。
- `web/motion-eval.js` 的复位不清表情动作、交叠、仪态、情绪体态这些状态，连着跑的场景之间可能带过去。

**怎么读：**
- **动作来源本身很便宜。** 运动匹配一次 0.35–0.5 ms，每 0.1 秒一次，摊到每帧（60 fps）不到 0.1 ms。待机和手势播放约 0.01 ms。所以 R1 省的不是时间，是内存（中性库 + 待机 52 MB → 几 MB），而且以后扩库内存不跟着涨，还给 R2 一个能求导的接口。
- 新动作来源每帧的预算：主线程 P95 ≤ 1 ms。
- 拿放、坐下的痛觉和像真人分最差。光凭这两个分数说不清原因：片段本身、IK 把片段拉到目标、家具碰撞都有可能。要按痛觉各项和运动仲裁表（`web/arbiter.js`）的分层权重再拆（记忆"查痛觉来源的做法"）。
- 高兴、生气、害羞、平静几种步态的冲击是中性的 3–7 倍，值得单独看（不在这个研究的范围内，记给动作会话）。

## 5. 研究方案

总原则：
- 每一步都和现在的系统在同一个服务、同样的种子、同一个脚本（`tools/motion_baseline.mjs`）里 A/B，从快照跑、记版本。
- 耗时 A/B 交替跑（A、B、A、B），在同一时段比。
- 失败的方向也记下来（知识库 `07 实验与评测/动作生成模型实验记录`）。
- 新动作来源不顶替旧的，先并排放着，用开关选。
- 行动层的接口改动要和改 `web/locomotion.js` 的动作会话商量好再做。

### R1：蒸馏成 Learned Motion Matching 式的小网络

**范围先缩小**：
- **R1a（第一步）**：只做中性风格的移动库（46.3 MB）加待机库（5.6 MB）。
- **R1b**：留得住再扩到其他 5 种风格。
- **R1c**：再扩到手势。
- 每一步留不留看实测。动作库（坐、拿放，2.4 MB）不在 R1 里：它们要和家具精确对齐，放到 R3。

**先分清两种目标**：
- **压缩**（R1a 的目标）：只是用更小的东西代替现有的库。可以拿全库训练；验收看闭环评估里的表现和重建误差。这样做出来的结果，只能说"能代替这个库"。
- **泛化**：要说"能对付新动作、新场景"，测试集就得按原始动作来源单独留出来（整段 BVH / CMU 的整个 trial / StayStill 的整个受试者），训练前定好名单，记进实验记录。像真人分参照集里"每 5 段留 1 段"是给打分用的，不会自动变成新模型的留出集。R1a 不做泛化的结论。

**做法**（照论文自己写，不抄示例数据）：
- **特征**：现有的 27 维匹配特征（未来轨迹、脚、髋速度），加类别标签（走、待机、换重心……）。待机本来按片段编号播，改成"按标签查"。标签就是 R2 指令嵌入的雏形。R1b 再加风格独热。
- **4 个网络**：
  - 压缩器：姿态 → 潜变量，约 32 维，只在训练时用；
  - 解压器：特征 + 潜变量 → 22 根骨骼的 6D 旋转、髋、根速度、触地；
  - 步进器：预测下一帧的特征和潜变量；
  - 投影器：查询 → 最近的特征和潜变量，每 0.1 秒一次，代替现在的搜索。
- **训练**：每个网络是 2–4 层、256–512 宽的 MLP。超参数先照参考实现：50 万步，batch 32，步进器窗口 20 帧。
- **推理**：新文件 `web/lmm.js`，用 Float32Array 手写矩阵乘，不加依赖。权重文件存成 16 位整数。切换用 `?motion=lmm` 或配置项。惯性化照用 `mm.js` 的 `Inertializer`。
- **对照组**：加不加 DeepPhase 式的相位特征；待机蒸馏进去 vs 待机留着片段播放。
- **数据**：`models/motion/neutral.*`、`idle.*`，本机已有，许可都能商用。不用 HAST-SEC，不用下载。
- **算力**：
  - 环境：本机 `runtime/train-venv`（PyTorch 2.11 + CUDA 12.6，已装，有 numpy）。
  - 显存：估计 < 1 GB，可以和 TTS（2.6 GB）、本地大模型同时开；也能在 CPU 上训。
  - 时间：每个网络几十分钟到几小时（估计，没测）。
- **预期大小**：
  - R1a 运行时只带解压器、步进器、投影器，约 120–160 万参数；
  - 16 位文件约 2.5–3 MB；载入后展开成 Float32 约 5–6 MB，加上中间结果。
  - 这三个数（文件、运行时占用、载入峰值）分开量、分开报。
- **验收**（silvercat，3 个种子，从快照跑；和第二版基线比）：

| 项 | 门槛 |
|---|---|
| 运行时占用 | 中性库 + 待机：≤ 8 MB（基线 51.9 MB）；文件大小、载入峰值另外报 |
| 动作来源每帧耗时 | 主线程 P95 ≤ 1 ms；整帧平均和基线交替跑，差不超过 0.5 ms |
| 像真人分 | 待机、说话、走、走到目标、坐、拿放：每项 ≤ 基线 + 0.05 |
| 痛觉每帧平均 | 每项 ≤ 基线 × 1.1；脚打滑 ≤ 基线 × 1.2；冲击 ≤ 基线 × 1.1 |
| 走到目标 | 27/27；离站位 ≤ 0.25 m；朝向差 ≤ 5° |
| 延迟 | 根动 2 cm ≤ 100 ms（基线 83）；到 0.4 m/s ≤ 450 ms（400）；换目标偏开 20° ≤ 100 ms（50）；停下 ≤ 800 ms（733）；转过 90° ≤ 450 ms（383） |
| 不碰的部分 | 手势、表情动作照旧，结果不变 |
| 体检全套 | 原来能完成的场景都能完成 |

- **风险**：
  - 步进器会漂。对策：投影器每 0.1 秒重新对齐一次。
  - 待机的细小动作可能被抹平，要看像真人分里待机那一项。

#### R1a 实际怎么做的（2026-10-27）

- **训练**：`tools/train_lmm.py`，在 `runtime/train-venv` 里跑，PyTorch 2.11 + CUDA，本机 RTX 3060。
  - **中性库**：压缩器（姿态和速度 → 32 维 z，512 宽，只在训练时用）和解压器（[x, z] → 22 根骨骼的 6D 旋转、髋、根部运动、触地）一起训。
    - 损失：6D 值、骨骼指向（旋转乘标准方向）、相邻帧差、触地交叉熵、z 的大小和逐帧平滑。
    - 步进器：按 20 帧窗口展开训，权重照参考实现。
    - 投影器：输入是加噪的查询，一半换成另一帧的轨迹；目标是这个查询在库里的真最近邻（只在可搜索的帧里找，和 `mm.js` 一样）；另外加一项"代价要准"的损失，因为运动匹配要拿它和"接着播"的代价比。
  - **待机库**：它按片段编号播、不搜索，所以没用步进器，改成每 8 帧一个关键帧 z、中间线性插值，解压器直接学插值出来的 z。
    - 取哪一帧都是一次解压，不会漂，也不会在关键帧处跳。
    - 触地标记照抄原库（54 KB），行动层的 `_liftSoon` 直接往后读。
  - 解压器、步进器、投影器先试 256 宽（每帧耗时的预算），512 宽当对照。
- **导出**：一个 `.bin` 文件，头部是 JSON，权重是 16 位整数加每行一个比例。
  - 文件名只用小写字母、不配 `.json`：服务端 `/motiondb/` 只认这种名字；有同名 `.json` 的 `.bin` 会被当成一种风格。
- **浏览器**：`web/lmm.js`。
  - `LMMNeutral`：搜索交给投影器；播放时步进器用到哪一帧推到哪一帧，解压器解出姿态。帧号放在 4 个槽 × 256 帧的小窗口里，每次搜索占一个新槽（正在播的槽不动），播到槽尾时行动层自己会强制再搜一次。
  - `LMMIdle`：片段和帧号和原库一样。
  - 权重运行时也是 16 位，不展开成 Float32。手写矩阵乘的速度和 Float32 一样，约 0.8 GMAC/s。
- **接入**：`web/mm.js` 的 `samplePose`、`search` 各加一行，库对象自带 `sample` / `search` 就交给它；`web/locomotion.js` 不改。
  - A/B 时由 `motion_baseline.mjs --motion lmm` 在页面里调 `installLMM` 换库。
  - 换之前先用原来的库把像真人分的参照集算好，两边用同一个参照。
- **核对**：`tools/lmm_check.mjs`。
  - JS 和 PyTorch 对得上（16 位量化带来的最大差约 1e-4）；
  - 量每个网络的耗时；
  - 拿原库当真值，量"投影 → 播 2 秒"的骨骼指向误差。
- **对比**：`tools/motion_ab.py` 把几轮结果按动作来源分组，列表，并按上面的门槛逐条判。
  - 同一个快照（网络文件只放在快照里，没进仓库的 `models/motion`）、同一个服务；
  - base / lmm / lmm-neutral（只换中性库，待机照旧播片段）交替各跑两轮。

#### R1a 第一版的结果（2026-10-27，256 宽，没过门槛）

**训练**：
- 全量 101 分钟，其中有一段和 512 宽的对照并行，互相拖慢；512 宽的训到一半停了，按估算它每帧要超预算。
- 显存峰值 0.78 GB。
- 记录在 `logs/motion-model/r1a-train-h256.json`。

**离线**（`tools/lmm_check.mjs`）：
- JS 和 PyTorch 最大差 7e-4。
- 中性库：
  - 解压器单独用：骨骼指向平均差 0.50°，触地准确率 0.99；
  - 从一帧自己的特征投影过来就差 4.3°（投影器的近似误差）；
  - 往后推 2 秒 7.7°、4 秒 10.1°、8 秒 11.9°。
- 待机：0.34°，逐帧变化幅度和真值一样（没有关键帧台阶）。
- Node 里模拟播放：每帧 P95 0.97 ms。

**A/B**：
- 同一个快照（代码 `6e552348…`），整机 CPU 忙 14–17%。

#### R1a 第三版（压缩的匹配库，不用投影器和步进器）

- **做法**：搜索、换段和原来的运动匹配完全一样，只是存储换掉：
  - 匹配特征量化成 8 位，精确搜索，按 16 帧分块剪枝；
  - 每 2 帧存一个 8 位潜变量，中间插值，解压器出姿态；
  - 触地标记照抄原库。
  - 压缩器、解压器直接用第二版的检查点（`train_lmm.py --only match --resume`），不用重训。
- **代价**：占用随帧数线性涨，每帧约 43 字节（原来约 310 字节），不再是 LMM 那种"多少数据都是这么大"。
- **离线**：
  - 潜变量间隔：每帧 0.65°、隔 2 帧 0.69°、隔 4 帧 0.95°，选隔 2 帧。
  - 文件 6.55 MB，运行时 7.21 MB（槽长 64）。
  - 和原库的搜索比，84% 是同一帧，其余代价平均只高 5%（8 位量化让最近邻挪了一点）。
  - 搜索耗时和原库一样，0.73 ms。
- **A/B**：
  - 换段次数和原库几乎一样（走路 33 对 34）。
  - 冲击反而全面变大（走路 60 对 41，停下 23 对 4）。
- **两个变体**：
  - 变体 1：根部运动照原库存，16 位，每帧 6 字节；
  - 变体 2：在变体 1 上，特征再改成 16 位。
  - 变体 2 的走路是所有方案里最好的（痛觉 0.104、打滑 0.117、冲击 40.4，都不比原库差）。说明 8 位特征的量化噪声进了解压器，冲击就是这么来的。
  - 但走到目标、转身、停下的冲击仍然大很多，停下要 1.3 秒，中性库占用 12.3 MB。
- **结论**：❌ 第三版不留。

#### 延迟的测法问题（R1a 中途查到的）

- **现象**：三个版本换目标都"慢了 180–270 ms"，有的种子测不到转向。
- **查下去**：测不到的那几次，对照段的方向抖动是 158–172°。网络版起步时先往前走、边走边转向目标，速度到 0.4 m/s 那一刻还在转弯。
- **改法**：要等走稳（第 3 节）。
- **结果**：原库本身换目标要 233 ms；第二版是 200 ms，并没有变慢。"慢了 230 ms"的结论撤回。

#### R1a 的结论（2026-10-27）

（2026-10-28 注：这一节的页面 A/B 都带着评估的跨场景残留和网络版的待机槽问题，见"R1a 定位轮"开头；差得小的项不可靠，要按定位轮复核那批看。）

- **没有一个版本全部过门槛。** 最好的候选是第二版加偏置 0.1：

| 项 | 结果 |
|---|---|
| 占用 | 中性库 46.3 → 1.85 MB，待机 5.6 → 0.73 MB，合计 52 → 2.6 MB（20 倍） |
| 耗时 | 每帧动作来源 P95 约 0.5 ms（交替跑时整帧不变） |
| 延迟 | 起步、换目标、转身、停下都在原库 × 1.2 + 一帧以内 |
| 比原库好 | 走到目标的痛觉低 43%，转身的痛觉低 64%，走路的痛觉、打滑也略低 |
| 比原库差 | 坐下、拿放的痛觉高约 25%，拿放冲击高 36%，走到目标、换目标、停下时脚打滑多 37–80%，待机网络有 0.8 mm 级的"重心出支撑面" |

- **差的地方，原因拆到了这一步**：
  - **坐下**：主要是"重心出支撑面"（0.60 → 1.03）。走到沙发前最后几步的站姿和坐下片段接不上。
  - **拿放**：主要是接触层把手臂推出身体（2.5 → 4.0）、手臂插进身体（0.14 → 0.32）。解压出来的手臂离身体近了几度，碰上动漫角色的宽胯就穿。
  - **打滑**：触地标记来自投影器，准确率 0.93（解压器单独用是 0.99），脚锁跟着标错。
- **留不留**：网络文件和检查点放在 `models/motion/r1a/`（v1、v2），结果在 `logs/motion-model/r1a/`。都没换进行动层，网页和桌宠照旧用原来的库。
- **下一步可选**：
  1. 触地单独训一个小分类器，或在解压器、投影器里加重触地的权重。治打滑。
  2. 骨骼指向损失按手臂、脚加权，加一项"手臂别贴身"的约束（用接触层的身体胶囊）。治拿放的穿插。
  3. 走到座位、台面前的最后几步还用原库（换库只在走路中段）。确认坐下、拿放的问题是不是出在交接处。
  4. 接受现状：把"手臂穿插、脚打滑交给接触层和脚锁"写进验收，只看最终的痛觉总量。按偏置 0.1 的数，走路、走到目标、转身更好，坐下、拿放更差，总体差不多。

**三种体型合起来的结论**（图 `logs/motion-model/r1a/figures/`：`four_groups_pain.png`、`four_groups_terms.png`、`arm_out.png`、`contact_timing.png`）：

1. **触地单独训（g2）：** ❌ 三个体型上都和 g1 没有稳定差别，离线的着地、离地时刻也几乎不变（85.5% → 85.8%）。问题在状态的相位，不在判法。
2. **手臂约束 + 步进器、投影器微调（g3）：**
   - 坐下在三个体型上都回到原库水平或更好；
   - 拿放的"手臂被推开"一个也没降下来（silvercat 119 → 106、miomio 140 → 130、wendy 389 → 417，原库 76 / 50 / 214）；
   - 停下（miomio、wendy）和转身（silvercat、miomio 的两腿穿插）变差。
   - 微调里同时有一般的姿态损失，好坏分不出来各是哪一项带来的。要分开，得再加一组"只加姿态损失、不加手臂项"。（定位轮补了 g3p：转身、停下变差来自姿态损失；坐下随体型变；手臂项在页面上没有稳定的好处。）
3. **手的位置：** 五组在三个体型上都和原库一样（差别 ≤ 0.8 cm）。托腮、捧脸、比心、坐着手放腿上这些合法接触没被破坏（更正：表情动作期间网络没在跑，这一点没测到；离线查是被往外拉了，见定位轮第 4 项），但约束在闭环里也基本推不动手。拿放的穿插有多少取决于体型（wendy 最多），在标准骨架空间里加约束够不着。要把体型（身体胶囊）带进约束，或者干脆交给运行时的接触层。
4. **g1 和原库比，在三个体型上一致：**
   - 更好：走、走到目标、换目标、转身（转身痛觉 silvercat −63%、miomio −30%、wendy −67%）；
   - 更差：坐下、拿放（动作交接处）、待机的重心（边界效应，wendy 最明显）。
   - 起步：silvercat 117 ms、miomio 133 ms、wendy 350 ms（原库 83–100 ms）。
5. **研究重点（按用户的评估）：** 接触相位、体型、动作交接三件事都定位到了，但这轮两个办法都没解决。下一步：
   - **接触相位：** 状态里显式带每只脚的相位，触地由相位推出来。可借 DeepPhase 的周期自编码器，或者先从原库的触地标记推一个简单的步态相位当额外特征，和 g1 比时刻误差。
   - **体型：** 约束要带体型。训练时随机采样身体胶囊尺寸，或者让运行时接触层的修正量反过来当损失。
   - **交接：** 坐下、拿放前的最后几步还用原库，确认问题是不是在交接处（定位轮做了：都不是主要坏在交接）。

**1. 原始编码状态和投影状态分别解码：错误是不是从投影进来的？**

| g1 | 姿态误差 | 着地 / 离地对上 | 平均差（帧） | 相位滞后（帧） | 短于 4 帧的触地段 |
|---|---|---|---|---|---|
| 真编码直接解码 | 0.49° | 99.3% / 99.1% | 0.18 / 0.20 | 0.15 | 2.1%（真值 1.75%） |
| 每帧投影后解码 | 4.08° | 98.0% / 97.1% | 0.47 / 0.62 | 0.50 | 3.6% |

- 解压器本身没问题。**姿态误差主要是投影带进来的**（0.5° → 4.1°）。
- 投影对触地时刻影响小：对上的比例只差 1–2 个百分点，时刻差半帧。

**2. 单步和连续多步生成对比：步进会不会累积相位偏差？**

| g1（按离起点多少帧分段） | 姿态误差 1–14 / 15–29 / 30–60 | 着地对上 | 相位滞后（帧） |
|---|---|---|---|
| 单步（每步都从真状态推一步） | 0.90°（各段一样） | 99.2% / 99.2% / 98.3% | 0.36 / 0.34 / 0.23 |
| 多步，从真状态起 | 2.2° / 3.4° / 5.3° | 97.7% / 96.5% / 86.7% | 0.73 / 0.99 / 1.89 |
| 多步，从投影状态起（= 运行时的固定段） | 4.3° / 5.0° / 6.6° | 95.8% / 93.3% / 80.0% | 1.18 / 1.62 / 2.50 |

- **会累积。** 单步只有 0.9°、0.3 帧；连续推 2 秒，相位滞后涨到 1.9 帧，着地对上的比例降到 87%。
- 从投影状态起步，起点就差 0.5 帧，再叠加步进的累积。
- 页面里一段平均只播 9 帧左右（silvercat 走路 422 步里换段 46 次），落在 1–14 帧这一档：姿态 4.3°，滞后 1.2 帧，其中约一半是投影起点带来的。
- 所以第四轮"漂移不是主要问题"那句只对页面里的短段成立。以后如果要播长段（比如为了少换段），步进器的累积就会变成主要问题。

**3. 固定片段和频繁重新投影对比：换段会不会破坏接触时序？**

每 3 帧（0.1 秒）用"真片段的未来轨迹 + 当前状态的姿态特征"建查询，和行动层一样。另跑一遍给轨迹部分加噪声（标准化单位 0.3）：不加噪声时原库永远是当前帧最好、一次都不换，看不出"换段本身"的影响。另加两种换段规则：偏置从 0.1 提到 0.3；"触地一致才换"，即候选状态解出来的两只脚着地和当前一样才换（规则不用重训）。

| g1，60 帧平均 | 每秒换段 | 着地 / 离地对上 | 每只脚每秒多出来的事件（着地 + 离地） | 短于 4 帧的触地段 |
|---|---|---|---|---|
| 原片段（真值） | — | — | — | 1.75% |
| 网络固定段（不换） | 0 | 87.0% / 83.8% | 0.21 | 1.7% |
| 网络按运动匹配规则换 | 2.6 | 91.6% / 90.5% | 0.22 | 6.8% |
| 网络每 3 帧都换 | 10 | 88.5% / 86.0% | 0.38 | 19.7% |
| 网络按规则换，偏置 0.3 | 1.9 | 91.3% / 90.1% | 0.21 | 5.5% |
| 网络按规则换，触地一致才换 | 2.5 | 90.3% / 89.4% | 0.17 | 2.2% |
| 查询加噪声：网络按规则换 | 6.0 | 89.9% / 87.8% | 0.32 | 13.8% |
| 查询加噪声：偏置 0.3 | 4.0 | 90.3% / 88.6% | 0.27 | 10.1% |
| 查询加噪声：触地一致才换 | 5.5 | 88.6% / 86.6% | 0.20 | 2.7% |
| 查询加噪声：原库按规则换（精确最近邻） | 2.9 | 97.0% / 95.9% | 0.12 | 6.25% |

- **按规则换段对时刻是好事：** 它把累积的漂移拉回来，着地对上的比例从 87% 升到 92%。
- **但换段会把触地切碎：** 短于 4 帧的着地段或离地段从 1.7% 涨到 6.8%，每次都换涨到 20%。这种碎段让脚锁一会儿锁一会儿放，是页面里过渡处打滑的来源之一。
- **原库换段也会切碎（6.25%）**，所以这部分是运动匹配本身就有的。
- **网络特有的问题：** 同样的带噪声查询，网络换段次数是原库的两倍（6.0 对 2.9 次/秒），碎段也是两倍多（13.8% 对 6.25%）。投影器的代价估计噪声大：偏置 0.1 在干净查询下够用，查询一有噪声就不够。
- **偏置提到 0.3** 少换了三分之一，碎段只降到 10%；页面里偏置 0.5 已经让停下变成 1.3 秒（见"投影代价偏置"）。
- **"触地一致才换"** 换段只少 5–8%，碎段却降到 2.2–2.7%，比原库还少，每只脚每秒多出来的事件也少了 0.05–0.12。代价是着地对上的比例低约 1 个百分点（换段少了，漂移拉回得少）。

**g3、g3p 在 1–3 项上和 g1 几乎一样**（多步从真状态起 3.9° 对 4.07°，滞后 1.8 对 1.9 帧，其余各项相差都在 0.5 个百分点以内）。g4 带的触地分类器各情况只比解压器自带的高 0.2–0.4 个点：状态本身的相位已经偏了，换个读法读不回来。

**4. 补"只加姿态损失"的对照（g3p）：g3 的改善到底来自哪一项？**

| 手臂项 | 页面上没有稳定的好处；离线把本来贴身的手往外拉一倍 | 去掉 |

三个候选方向的证据：
- **改投影器（证据最多）：**
  - 姿态误差主要从这里进来；页面里每段的起点都来自它；它的代价估计噪声大，导致换段多、触地碎。
  - "触地一致才换"在 silvercat 上的效果说明：起点和当前步态的相位接得上，坐下、转身、停下都能大幅变好。硬闸门只是拦掉接不上的候选，不会产出接得上的候选，所以对体型不稳。
  - 要改的是投影器本身：输入里加当前状态（或当前每只脚的触地），让投影出来的起点和当前相位接得上；用带噪声的查询训，让代价估计更准（目标：带噪声时换段次数接近原库的 2.9 次/秒）。
  - 不训练的过渡办法：换段时触地不一致加一个软代价，先在三个体型上 A/B。
- **每只脚的相位（有证据，但不是页面上的主要问题）：** 状态的相位确实会漂（2 秒 1.9 帧），换读法读不回来（分类器只高 0.2–0.4 个点）。但页面里一段只播约 9 帧，漂移影响小。它更像是"以后要播长段、要让动作层按相位起步"时的前提。按评审的意思，不能因为分类器没用就认定相位一定能解决。
- **体型和几何约束（问题明确，但现在的约束形式不对）：** 拿放时东西压进胸口，在三个体型、两批、各个种子上都稳定（wendy 最多），silvercat、wendy 上网络版是原库的 8 倍和 3.4 倍，miomio 的原库没有这一项。标准骨架上的手臂项没用。下一步先量端着东西走路时网络版和原库的上身姿态差在哪（躯干前倾、手的高度），再决定约束怎么加。这一步只量，不训练。

另外两件不在网络这边，记给动作会话：
- 坐下：行动层不管步态相位就开始坐，原库在 miomio、wendy 上也会单脚起坐。等双脚着地再坐，原库、网络都受益。
- 起步：网络版起步时根部动 2 cm 的时间，在复核那批里三个体型都过不了门槛（133 / 150 / 183 ms，门槛 117 / 117 / 137 ms）。第四轮已经报过 miomio、wendy，本轮 silvercat 也超了。

### R2：按指令嵌入和根目标的自回归生成模型（混合表示）

- **目标**：不再"从库里挑片段"，而是生成。可以按指令、根目标、约束组合出库里没有的过渡，中途换指令。
- **两个方向 A/B**：
  - **R2a，ARDY 精简版**：
    - token：每 4 帧（30 fps）一个，内容是根 5 维 × 4 帧，加身体潜变量。分词器用 FSQ，比 ARDY 小（例如 32 维）。
    - 两段去噪：根 Transformer 和身体 Transformer 各 4 层、宽 256、4 头。
    - 4 步 DDPM。生成窗 2 个 token（8 帧），历史最多 16 个 token（约 2 秒），远期目标作为额外 token。
    - 条件：我们自己的结构化指令（技能、风格、情绪）的嵌入（64 维），以及根目标和约束。动作网络针对这套指令从头训。
    - 合计约 800–1000 万参数：fp16 16–20 MB，8 位 8–10 MB。
  - **R2b，一步式**：CAMDM 的条件方式，去掉扩散；或者 MVAE 的专家混合解码器。每帧算一次，计算量小两个数量级。
  - 另试：把 R2a 蒸馏成 1–2 步（ARDY 提到的 shortcut 方向）。
- **运行方式**：
  - 生成放在 Web Worker 里，用 ARDY 那种重规划缓冲，渲染循环从不等它。
  - 估算 R2a 每次生成约 1.2 GFLOP（4 步 × 约 24 个 token × 约 600 万参数 × 2），每秒约 4 次，约 4–5 GFLOP/s。手写的标量 JS 不够，要 WebGPU 或 WASM SIMD。**这个数没实测**，R2 开头先做推理速度的原型。
  - 推理库（onnxruntime-web 等）是新下载，到时候再问。
- **数据**：
  - 本机 4.3 小时，加 100STYLE 全集（约 18.5 小时，1.47 GB，要下载，CC BY 4.0）。
  - 可选：更多 CMU 受试者、StayStill 玩手机待机。
  - BONES-SEED 要等许可核实。
  - 标签：不需要自由文本。指令就是意图模型的技能表加风格、情绪。风格来自 100STYLE 的文件夹名，类别来自 `build_motion_db.py` 已有的切分（坐、拿放、手势）。
  - 测试集按原始动作来源留出（同 R1 的规矩）。
- **算力**：
  - 600–1000 万参数，batch 256，训 20–40 万步，显存估计 2–3 GB。
  - 笔记本能跑，但要和 TTS、大模型抢，还要跑好几天。放到用户以后给的专门电脑上（见记忆"物理仿真+强化学习的计划"），或者用付费云端（先问）。
  - 分词器可以先在本机训。
- **预期大小**：R2a ≤ 24 MB（16 位），R2b ≤ 10 MB。
- **验收**：
  - R1 的全部门槛；
  - 指令正确率 ≥ 90%（训练集里有的技能，分类器判）；
  - 走着时换指令，300 ms 内出现新动作；
  - 主线程每帧 ≤ 1 ms；
  - Worker 每次生成的耗时 ≤ 生成窗时长的一半；
  - 模型 ≤ 24 MB。

### R3：约束、IK、接触层、小窝物理怎么接

- **约束进模型**（ARDY 的掩码约束）：
  - 根路径和路点：来自 `web/nav.js` 的寻路，代替现在的弹簧模拟骨；
  - 手：拿放、伸手时手要到的位置，来自场景；
  - 脚触地；
  - 坐下时的骨盆关键帧，来自座位。
- **先补数据，再谈约束**：拿放、坐下需要相应的数据覆盖。只给模型加一个"手到这里"的约束输入，保证不了它学会稳定抓持、接触和受阻恢复。
  - 现在动作库只有 16 段捡起、14 段放下、32 组坐下（含镜像）；
  - 手在 0.3–0.9 m 高度的拿放片段没有（待办里记着）。
  - R3 前要先补这些数据（动捕或合成），抓持稳不稳、受阻怎么办归小窝物理的 P2（可失败的抓持）。
- **表情动作改成"约束模板"**：现在 6 个表情动作各手写一段 IK。改成：模板 = 某些时刻手腕相对胸口、头的位置和朝向 + 手形名，由生成模型出全身动作，IK 只做最后 2 cm 以内的修正。
  - 新表情动作 = 新模板（数据），不是新代码；R4 让大模型写模板。
  - 验收：6 个现有表情动作用模板重做，手腕误差（`emote` 场景的 `extra.emote`）≤ 现在的 3 mm 水平，痛觉不升；`lat_heart` 的手形判据照样成立。
- **IK、接触、平滑、落地照留着当安全网**。新指标"IK 修正量"：用运动仲裁表量 IK 层让各部位转了多少。生成越准，修正量越小。
- **小窝物理**（`docs/roadmap/room-physics.md`）：
  - 生成模型给运动学目标，Rapier 管物件。端杯子时，"杯子别晃"是一个约束：手的加速度上限、杯口朝上。
  - 以后在专门电脑上训物理跟踪控制器，用生成模型当参考动作；痛觉各项当奖励惩罚，动捕参照集当 AMP 判别器数据。
- **认知和真值分开**：喂给生成模型的目标只能是她"认为"的位置（来自她的认知），不能直接读场景真值；双胞胎测试照样守着。

### R4：大模型把话变成指令和潜变量

- **意图模型照旧出结构化动作**（Qwen3.5-0.8B + LoRA，已常驻约 795 MB）。在 `do/side/to/amp/spd/at` 之外加可选字段：
  - `style`；
  - `motion`：技能表里没有的动作的一句描述；
  - `pose`：约束模板的名字或参数。
- **指令嵌入，不要 8B 编码器**：
  - 离线用本机已有的 bge-small-zh-v1.5（MIT）把技能名和描述编码，再和 R2 一起训一个投影到 64 维。浏览器里只放一张表（几十 KB）。
  - 新说法在服务端编码后经 WS 发一个 64 维向量（约 0.5 KB）。
  - 对照：Qwen3-Embedding-0.6B（本机已有）的嵌入。
  - 同 1.1 节的提醒：这个投影是和动作网络一起训的，不是拿来对齐别人的表示空间。
- **"说一句就生成"的新动作**：
  - 大模型写约束模板 + 选最近的指令嵌入，生成模型执行，痛觉和像真人分打分。
  - 不合格她自己调（按"让她自己学"：给她工作台里改模板、看分数的工具，成功的模板存成她的技能），不是我们替她写。
  - 和手写 IK 的 6 个表情动作 A/B。
- **验收**：
  - 30 句留出的动作描述（训练里没出现过的说法），约束满足、痛觉低于阈值、用户看了觉得对的比例；
  - 说完 → 动作开始、说完 → 听到声音的 P50/P95 不退化。

## 6. 未决和风险

- 视频看不到内容，"24 MB"没核实；作者代码还没公开。等公开了只读思路，不搬代码（作者的 HAST-SEC 是非商业的，新代码的许可要先看）。
- 我们的数据规模（4–20 小时）够不够训出 R2a 那样的扩散模型，不知道。最接近的证据是 CAMDM（100STYLE，约 18 小时，只做风格化移动）。
- 浏览器里 R2 的推理速度没实测。
- R1 要在 `web/locomotion.js` 里加一个"动作来源"的开关，那个文件动作会话在改，要先和它说好。
- BONES-SEED 的许可要用户自己登录看；BEAT2、Bandai Namco 的许可这次没重新打开原文。
- 这台机器上别的会话一直在跑东西：耗时只能同一时段交替比；版本要从快照跑才固定得住。
