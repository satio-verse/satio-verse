# 小窝的物理与后果机制

2026-10-27 方案；同一天 P0 做完（做法、数字见根目录 README"小窝的物理与后果 P0"一节，实验记录在知识库「07 实验与评测/物理与后果实验记录」）。用户："目前没有物理碰撞的引擎基础，导致角色碰到什么、撞到什么，不会有任何变化，比如咖啡杯不端稳里面的咖啡会洒、会烫到自己，会把桌子撞到、健身器材踢到一边或者伤到角色自己"，并要求把它提到下一阶段的**基础优先级**，排在自主生活（知识库「07 实验与评测/小流认知与自主生活落地方案」）前面。

三者的分工：**物理环境决定实际发生什么；世界模型（她的认知，`wm/cognition/`）预测可能发生什么；她从预测和结果的差异里学。** 大模型可以判断"这杯咖啡可能洒"，但洒没洒、洒在哪、剩多少，由环境算。这和根目录 README"认知与真值分离"一节是一回事：物理世界就是真值，她只能通过看到、碰到、烫到知道结果。

**顺序调整（2026-10-27，用户贴来的核查）**：
1. 先修动作评测的尺子，固定代码、数据、评分参照的版本（`docs/roadmap/motion-model.md` 的 R0）。
2. P1、P2 和 P4 的最小闭环并行：行动前预测 → 执行 → 感知后果 → 更新经验 → 下次提前调整。动作模型给目标，控制器执行，物理决定结果；交给物理的东西，动画不能再改写它的位置。
3. 第一个自主学习里程碑是"端咖啡的经历改变下一次的选择"：
   - 记下洒在哪个阶段（拿起、挪到身前、走、放下）。
   - 下次她自己挑：拿起放慢、开端稳、少装一点。
   - 换杯子、路线、装量，看经验能不能迁移；和清空经验的版本对照。
   - 程序不变，变化只来自她的经历。验收看送到、剩多少、用时、身体刺激，还要防"不走""先倒空"。
4. 感知的边界：精确的毫升、温度不进认知，她看见、碰到的证据要进。
   - 看得到杯口时给液面粗档。
   - 碰到时觉得烫，带部位。
   - 洒出的东西，看见了或落到身上才知道。
   - 先过感知这道门再决定报什么：把真值改写成"洒了不少"一样会泄露。
   - 双胞胎测试：只差感知不到的状态时，认知和决策要一样；有了看得见、碰得到的证据，允许、也应该不同。

## 3. P0：液体与后果（先做，不用下载；2026-10-27 完成）

做下来和方案不一样的地方：
- 杯子不直接跟着掌心：动画给的掌心位置一帧能跳 1–2 cm（算出来 30–50 m/s²），杯子按 4 Hz 临界阻尼弹簧跟着手，加速度最多 6 m/s²。
- 线性晃动模型在浪翻过杯沿以后会无限变大（急停一次把整杯洒光），翻出去的那截从振型里扣掉，最多比杯沿高 8 mm。
- 几滴热咖啡只算烫一下，溅上一毫升以上才算烫伤；嘴的门槛高 22 ℃（高 15 ℃ 时她每次喝刚冲好的咖啡都喊疼）。
- 评测台发现满杯洒得多主要是手跟着髋部一步一颠（和走多快关系不大），所以 P0 里顺带给行动层加了"端稳"（`carryCare`）：这是以后她要学的一个旋钮。
- 小屋里落到哪按房间模型往下照，不按场景盒子（地毯比地面高，一摊被盖住）。

下面是原来的方案。

杯子的运动（位置、朝向，每帧）从哪来都行：现在是掌心，P1 以后是刚体。所以液体模型先做，换引擎时不用重写。

- **晃动**：液面按一阶晃动的等效单摆算（每个水平方向一个阻尼振子）。杯子的水平加速度和倾斜是输入；圆柱杯的固有频率 ω² = (g·1.841/R)·tanh(1.841·h/R)，R 是杯半径，h 是液深。液面在杯沿的高度超过余量（杯高 − 液深）就往外流，流量按超出的部分算。
- **守恒**：洒出的量从杯里扣，落到地上、桌上、身上成一摊（有体积、位置、温度），慢慢干。粒子和水渍只画状态里真有的。
- **温度**：牛顿冷却，杯里和洒出去的各算各的。冷水和热咖啡洒的过程一样，后果不一样。
- **热接触**：洒出的液体碰到身体某处（手、腿），按温度和量给那个部位一个刺激，交给 `room-body.js`：先在本地做保护动作（缩手、停下、放下杯子，不等大模型），部位记"烫了一下"，过一阵恢复；恢复前那只手的握持变差。
- **持久**：杯里剩多少、多烫，地上和桌上的水渍，被挪开的家具，都存进小窝的状态。切到工作台、最小化、重开桌宠，都不重置。
- **必须成立的关系**（写成测试）：
  - 洒出的量不会凭空变多。
  - 空杯不洒。
  - 同样的走法，半杯比满杯稳。
  - 急转、急停比慢走洒得多。
  - 冷水和热咖啡洒的量相同，但只有热的会烫。
- **端咖啡评测台**：在网页版无界面评估里加场景 `carry`（`web/motion-eval.js`）。一张桌子、一只杯子、一段路、一个障碍。
  - 对比的条件：空、半、满杯；慢走、急转、急停；冷、热。
  - 记录：剩余液量、洒出量和落点、烫到没有、到没到。
  - 打分同时看"送到"和"少洒"，免得出现永远不动、或者先倒光再走反而分高的情况。

## 4. P1、P2 的要点

- **引擎**：Rapier JS/WASM（`@dimforge/rapier3d-compat`，2026-10-27 最新 0.21.0，Apache-2.0，npm 包解开约 15 MB，WASM 内嵌在 JS 里，WebView2 直接能载）。和 three.js 一样放进 `web/vendor/`，不走网络。**下载前要问用户。**
- **物件分类**：
  - 固定物件：墙、地、固定的器材。
  - 动态物件：杯子、球、小哑铃。
  - 有真实质量、摩擦、重心的动态家具：椅子、小桌，推得动但不会一碰就飞。
  - 带约束的：门、抽屉，用铰链或滑轨。
- **角色**：动画驱动的运动学胶囊（Rapier 的角色控制器），能推动态物件，但自己不会被推。
  - 这就是"无限力量"问题：动画坚持把手伸到某处时，桌子会被猛推开。
  - 所以手对物件施的力要有上限，超出就受阻、挪不动。
  - 交给物理的东西，动画不能每帧再覆盖它的位置。
- **房间缓存**：房间平时只画一次（`RoomCache`）。物件醒着（在动）时挪进活动层（`Props.live`），引擎让它睡下以后放回房间。这和现在"0.6 秒不动放回房间"是同一个口子。
- **抓持（P2）**：接近 → 接触成立 → 建立有力量上限的约束 → 受阻或力量不够就滑、偏、脱手。
  - "手指看起来握住了""系统请求握住""杯子实际被稳住"分开记，不能画等号。
  - 松手时杯子带着当时的速度。
- **后果要一直有效**：器材被踢到过道就成了新障碍，寻路要绕开；桌子挪了，原来放杯子的地方就不在了。

## 5. 和其他会话的分工

- **动作会话**（行动层 `web/locomotion.js`、`web/contact.js`）：P2 要改拿放，到时先对一下。P0 不碰行动层，只读掌心的运动。
- **认知会话**（`wm/cognition/`、`desktop/web/room-acts.js` 冲咖啡的脚本）：后果作为观察进它的事件流（P4）。
  - 双胞胎测试要覆盖：她的候选和提示词不能读液量、温度这些真值，只能读她看到、碰到的。
- **指标沿用**：痛觉各项、动作评估场景、调优闭环都继续用。全身动力学和强化学习留给那台专门的电脑，场景和指标照搬。
