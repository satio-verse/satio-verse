# 桌宠立项: 2D+3D 桌面陪伴 — 同一个角色从网页走到桌面

把阶段一在网页上做出来的角色 (同一份长记忆、同一条意图先行的语音闭环) 放到 Windows 桌面上常驻: 透明、置顶、可点穿、可拖动、有托盘;
3D (VRM) 和 2D (Live2D) 两种门面; 对外提供 OpenAI 兼容 API 和 MCP; 以 C ABI 的 `libwm` 为核心, 逐步把推理、语音、记忆存储和调度收进一个原生库.
前提是 **不妨碍阶段一的研发和科研, 也不影响实际产出** (见第 4 节).

本文最初是规划和环境摸底 (2026-10-24). 同一天用户确认下载 WebView2 SDK, M0 外壳验证已完成: 代码在 `desktop/`
(见 [desktop/README.md](../../desktop/README.md)), 实测结果见第 6 节"M0 实测".

## 1. 目标与成功标准

| 指标 | 目标 |
|---|---|
| 阶段一基准不退化 | 桌宠相关改动合入前后, `tools/bench_llm.py` (意图/开口延迟、动作准确率)、`tools/voice_loop_test.py` (说完 -> 听到声音 P50/P95)、长记忆端到端评测 (4 组剧本) 结果在噪声范围内: 延迟差 <= 20 ms, 准确率不降 |
| 桌宠的端到端延迟 | 说完 -> 听到声音 P50 比网页版多不超过 30 ms (同一个服务, WebView2 和 Chrome 是同一个内核) |
| 空闲占用 (不说话、不拖动) | 整机 CPU <= 1.5%, GPU 3D 引擎 <= 3%, 宿主 + WebView2 进程组内存 <= 350 MB, 渲染显存 <= 300 MB; 被全屏程序挡住或打游戏时 0 帧 |
| 窗口行为 | 透明像素处的点击落到下面的窗口, 角色身上能点、能拖; 置顶; 托盘菜单; 多显示器、125%/150% 缩放下位置和点穿都对 |
| 同一个角色 | 桌宠和网页共用同一份长记忆: 网页里说过的事桌宠答得出 (用 8792 端口 + 临时库的剧本测, 不碰真实库) |
| API / MCP | 官方 `openai` Python SDK 流式调用 `/v1/chat/completions` 通过; MCP Inspector 和至少一个真实 MCP 客户端 (Claude Desktop 或 Claude Code) 能列出并调用工具; 调用外部工具时, 有副作用的调用 100% 经过用户确认 |
| C 核心 | libwm 跑同一套 64 条意图基准, 动作准确率不低于 llama-server 路径, 意图延迟 P50 不慢; 单进程模式下不装 Python 也能聊天 |

## 2. 现状与依据

- **服务** `wm/` (aiohttp, `127.0.0.1:8790`): `/ws` 实时通道, 加上 `/api/status`、`/api/avatars`、`/api/resources`、`/avatars/*`、`/motiondb/*`、`/hpe/*`、`/static/` (就是 `web/`).
  一个 WebSocket 连接一个 `Session` (对话历史、ASR 会话、角色状态、能力声明都按连接算); 长记忆、嵌入、日志整理挂在 `Engines` 上, 所有连接共用.
  所以 **新客户端天然共用同一份记忆**, 不需要同步.
- **协议里桌宠用得上的** (README "WebSocket 协议"):
  - 上行 `capabilities`: 这个身体能做哪些技能. 2D 模型没有手臂时只声明头部动作, 服务端现有的过滤会把做不到的改判, 不用改服务.
  - 上行 `state`、`motion_eval`、`interrupt`、`text` 和 16 kHz PCM.
  - 下行 `intent`、`emotion`、`reply_delta`、`amend`、`face`、`prosody`, 以及带 20 字节头的音频帧.
- **前端** `web/` (约 5.7 千行 JS):
  - `VRMAvatar` 的渲染器已经是 `alpha: true` + `setClearColor(0x000000, 0)`, 背景本来就透明.
  - 模块里写死了服务端的绝对路径 (`/api/status`、`/avatars/`、`/motiondb/`、`/static/mic-worklet.js`、`/static/scenes/room.json`), 所以桌宠页面最好和服务同源.
  - `app.js` 是整页逻辑 (仪表、聊天面板、房间), 没有导出协议客户端, 桌宠需要自己的入口.
- **LLM 调用**: `wm/llm.py` 调 llama-server 的 `/v1/chat/completions`, 带 llama.cpp 的扩展参数 (`id_slot`、`cache_prompt`、`n_probs` + `post_sampling_probs`、`response_format` 的 JSON Schema、`chat_template_kwargs`).
  所有连接都用 0 号槽位 (`llm.id_slot`), KV 预热也按 0 号槽位做, 所以网页和桌宠同时说话会互相冲掉缓存、排队.
- **资源**: LLM (Qwen3.5-0.8B Q8_0, ctx 12288, parallel 3) 加上 Qwen3 嵌入服务, 常驻约 2.6 GB 显存.
  摸底时 (2026-10-24) 显卡已用 5877/6144 MiB, 有两个 llama-server 和两个 Python 进程 (其中应该有阶段一的 LoRA 训练). 所以桌宠第一版不能再往显卡上加模型.
- **Live2D 素材**:
  - SDK `character_models/CubismSdkForWeb-5-r.5.zip` 和模型压缩包都在 `character_models/` 里. 模型是 Eustia, VTube Studio 导出, Cubism 5 格式, 没有手臂参数.
  - Framework 的 59 个 TS 文件可以用 Node 22 自带的 `stripTypeScriptTypes` 编译, 没有外部依赖.
  - 接入本身是另一项待确认的工作, 本文只做规划.

**共性和结论**:
- **技术路线**:
  - 透明、置顶、点穿是标配. 现有项目分四类: Unity (Desktop Mate、MateEngine)、Electron (AIRI、Open-LLM-VTuber)、系统 WebView (BongoCat 用 Tauri)、WPF (VPet).
  - 我们选 **C/C++ 宿主 + 系统 WebView2**: 和 Tauri 一样不自带 Chromium (Windows 11 自带 WebView2 运行时), 又能直接复用现有的 three-vrm 前端.
- **让人一直开着它的理由**: 不是聊天本身, 而是"它知道我在干什么、记得我". 对应前台程序感知、日记、时间和节日、养成数值.
  我们已经有的: 长记忆、日期和农历生日、关系状态、空闲时整理日志. 可以直接长出"角色的日记"和"节日问候".
- **云端 API 的并发和成本**: 个人开发的 AI 桌宠最常出事故的地方 (《妹居物语》). 本地优先, 外接 API 只作可选项.
- **用户导入自己的模型**: 是刚需 (MateEngine、Desktop Mate 的 MOD、BongoCat), 但 Live2D 的"可扩展应用"许可要先问清 (第 8 节).

## 4. 怎么做到不妨碍阶段一、不影响实际产出

1. **独立目录 `desktop/`**: 宿主、桌宠页面、libwm、构建脚本、下载的 SDK 都放在里面. 不改 `wm/`、`web/`、`tools/`、`config/` 下的现有文件.
   必须改的几处 (下面第 3 条) 单独登记, 由改 `wm/` 的会话排期, 和阶段一的工作错开.
2. **桌宠只是现有服务的一个新客户端**:
   - 连 `ws://127.0.0.1:8790/ws`, 用和网页完全一样的协议.
   - 阶段一的改进全部通过同一个服务自动给桌宠用上, 桌宠这边不用跟着改. 包括长记忆、LoRA 后的 0.8B、回复侧检查、补动作、能力闸门; 前端模块的改进 (脚落地、调姿、平滑) 桌宠页面直接复用.
3. **协议只做向后兼容的加字段**: 新的上行消息老服务忽略, 新的下行字段老前端忽略, 不改已有字段的含义. 预计要加的:
   - `state.place: "desktop"`: 桌面上没有房间, 服务端换成"桌面"场景, 不往提示词里放沙发、电视;
   - `state.desktop: {"app": "编辑器|浏览器|游戏|视频|聊天|其他", "idle_s": ...}`: 前台程序类别, 用户打开开关后才发;
   - 上行 `say: {"text"}`: 固定文本直接合成 (不过 LLM, 仍过回复侧检查), 给 MCP 的"说一句话"用. `pipeline.py` 里已有 `_speak` 这条路;
   - 只读的记忆 HTTP 接口 (检索) 和只追加的写接口, 给 MCP 的记忆工具用.
4. **同源但不改服务**:
   - 宿主让 WebView2 打开 `http://127.0.0.1:8790/pet/`, 用 `WebResourceRequested` 拦截 `/pet/*` 这一前缀, 从 `desktop/web/` 读文件返回; 其他路径照常走服务.
   - 这样前端模块里写死的 `/api/status`、`/avatars/`、`/motiondb/`、`/static/...` 都能用, 没有跨域, 服务端零改动.
   - 备选: 以后服务端加一条只读静态路由.
5. **测试不碰真实服务和真实库**: 桌宠的自动测试另起一个 mock 服务, 端口 8794 (M1 起; 8792 是各会话测试常用的端口, 会撞车). 不往 8790 发测试对话, 不往 Obsidian 库写测试数据.
   - 自检时页面静音输出: mock 的 TTS 只发元音占位音, 不能放到用户的扬声器上;
   - 自检脚本里 `memory.vault` 置空 (不开记忆库);
   - 延迟和社交日志 (`trace.log_dir`) 指到 `desktop/build/selftest/logs`. M1 出过一次 mock 对话写进共享 `logs/` 的事, 见第 6 节.
6. **显卡让给阶段一**:
   - 第一版桌宠不加载任何模型, 只渲染.
   - 托盘里一键"暂停渲染", LoRA 训练或评测跑着的时候用.
   - 桌宠永远不去启停 llama-server, 不杀别人的进程.
7. **同一时间只让一个客户端出声**: 0 号槽位是共用的 (第 2 节). 托盘里标明当前由哪个客户端说话. 真要并行, 再加一个配置项给桌宠单独的槽位, 默认值不变.
8. **回归门槛**: 凡是要碰 `wm/` 或 `web/` 的桌宠改动, 合入前跑阶段一的同一套基准 (用 8792 的 mock 或离线评测脚本), 不退化才合入. 沿用路线总则.
9. **时间上错开**: M0-M2 的代码全部在 `desktop/` 里. M3 起的 libwm 是"可选引擎", 默认关闭, 阶段一照常用 llama-server.

## 5. 架构

### 5.1 总图

```
┌─────────────── desktop/host (C++: Win32 + WebView2) ───────────────┐
│ 透明置顶窗口 · 按角色像素点穿 · 拖动 · 托盘 · 全屏/游戏时隐身          │
│ 前台程序类别 (可选, 默认关) · OpenAI 兼容 API · MCP 服务端 (M2)       │
│  ┌──────────────── WebView2 ────────────────┐                      │
│  │ http://127.0.0.1:8790/pet/  (宿主从 desktop/web/ 返回)            │
│  │ desktop/web/pet.js                         │                      │
│  │  ├ 3D: 复用 web/ 的 VRM、动作、口型、说话表演                       │
│  │  └ 2D: Live2D Cubism Web + 自写驱动 (待确认)                       │
│  └───────────────────┬────────────────────────┘                     │
└──────────────────────┼──────────────────────────────────────────────┘
                       │ ws://127.0.0.1:8790/ws  (和网页同一个协议)
  网页 (现有) ──────────┤
                       ▼
  wm 服务 (Python, 阶段一主线): 长记忆 · 回复侧检查 · 补动作 · ASR/TTS · A2F · 埋点
     └─ LLM: llama-server (现在) | libwm (M3 起可选, 进程内)
  外部 MCP 服务 ◄── 桌宠的 MCP 客户端 (M5, 有副作用的调用都要用户确认)
```

单进程模式 (M4) 下, 宿主直接链接 libwm, 自己在本机端口上提供同样的 `/ws`. 页面不知道对面是 Python 还是 C.

### 5.2 外壳 `desktop/host` (C++17)

- **窗口** (M0 实测选定):
  - 无边框 `WS_POPUP`, 扩展样式 `WS_EX_TOPMOST | WS_EX_TOOLWINDOW | WS_EX_LAYERED`. `WS_EX_TOOLWINDOW` 让它不进任务栏和 Alt+Tab; 分层窗口用 `LWA_ALPHA` 255, 点穿必须要它.
  - 普通 HWND 宿主: 用 `DwmEnableBlurBehindWindow` 配一个空区域, 让 DWM 按像素透明度合成窗口; WebView2 的 `DefaultBackgroundColor` 设成全透明.
  - composition 宿主 (`CreateCoreWebView2CompositionController` + DirectComposition + `WS_EX_NOREDIRECTIONBITMAP`) 也通过了自检, 但鼠标要宿主自己转发, 留作备选.
- **点穿 (按像素)**:
  - 页面把角色的命中掩码 postMessage 给宿主: 每格 6 CSS 像素 (本机 70×120 格), 有角色的格外扩一格.
    每 250 ms 算一次, 变了才发, 没变也每秒重发一次. 拖动时窗口和角色一起动, 掩码不变, 不用更勤.
  - 宿主 30 Hz 查光标位置. 落在掩码里就去掉 `WS_EX_TRANSPARENT` (能点能拖), 否则加上 (点击落到下面的窗口).
  - 掩码过期时默认穿透: 宁可点不中, 不挡住用户.
  - 不用 `WM_NCHITTEST` 返回 `HTTRANSPARENT`, 它只对同一线程的窗口有效.
- **拖动**: 在掩码里按下左键, 宿主接管 (`SetCapture`, 移动窗口), 页面播"被拎起"的姿态. 松手后找脚下的"平台" (任务栏顶边、窗口标题栏顶边、屏幕工作区底边), 用现有的按鞋底落地站上去.
- **窗口大小**:
  - 第一版是跟着角色走的小窗口 (约 420×720 逻辑像素, 按模型包围盒定), 不是全屏覆盖层. 全屏透明 WebGL 在 4K 下太贵.
  - 角色在桌面上走动 = 宿主平移窗口 + 页面播原地步态 (复用 `GAIT` 的步幅/步频).
- **托盘** (`Shell_NotifyIcon`): 显示/隐藏、免打扰 (不主动说话)、静音、麦克风、3D/2D 切换、选角色、大小和透明度、在浏览器里打开完整页面、暂停渲染、退出.
- **全屏、游戏、演示**: 每 2 s 调一次 `SHQueryUserNotificationState`. 遇到 `QUNS_BUSY`、`QUNS_RUNNING_D3D_FULL_SCREEN`、`QUNS_PRESENTATION_MODE` 就隐藏, 页面降到 0 帧, 并停止枚举窗口.
- **前台程序感知** (学《妹居物语》, 默认关):
  - `GetForegroundWindow` -> 进程名 -> 本地映射表 -> 类别.
  - 只发类别, 不发窗口标题和进程名. 进 `state.desktop` (需要协议加字段).
- **其他**: Per-Monitor DPI V2; 多显示器各用各自的工作区. 只用公开的窗口 API, 不注入、不读别的进程内存.

### 5.3 桌宠页面 `desktop/web`

- **页面**: `pet.html` 用自己的 import map, 指向 `/static/vendor/...`.

**C ABI 草案** (`desktop/libwm/include/wm.h`, 只有 C 类型和不透明句柄):

```c
typedef struct wm_engine  wm_engine;
typedef struct wm_session wm_session;
/* 一条下行消息: json 和 /ws 下行 JSON 相同; 音频帧时 bin 是 20 字节头 + int16 PCM */
typedef void (*wm_event_fn)(void *user, const char *json, const void *bin, size_t bin_len);

int  wm_engine_create(const char *config_json, wm_engine **out);   /* 0 成功, 负数是错误码 */
int  wm_engine_load(wm_engine *e, const char *part);                /* "llm" "embed" "asr" "tts", 按需加载 */
int  wm_engine_unload(wm_engine *e, const char *part);
void wm_engine_destroy(wm_engine *e);
int  wm_session_open(wm_engine *e, wm_event_fn cb, void *user, wm_session **out);
int  wm_session_send_json(wm_session *s, const char *json);          /* 和 /ws 上行 JSON 相同 */
int  wm_session_send_audio(wm_session *s, const int16_t *pcm, size_t n); /* 16 kHz 单声道 */
void wm_session_close(wm_session *s);
int  wm_memory_search(wm_engine *e, const char *query, int top_k, char **out_json);
void wm_free(void *p);                                               /* libwm 分配的内存由它释放 */
const char *wm_version(void);
```

**为什么是"C 接口、内部可用 C++"**:
- **C ABI 是 Windows 上唯一稳定的跨编译器、跨语言边界**. Python (ctypes/cffi)、C#、Rust、Node、Unity 都能直接调.
  C++ 的 ABI 在 MSVC 和 MinGW 之间、不同版本之间都不兼容.
- **依赖本身是 C++**: Cubism Native Framework 是 C++ 源码, WebView2 是 COM 接口 (官方示例和 WIL 都是 C++), llama.cpp 内部是 C++ (对外是 C API).
  用纯 C 去调 COM (`lpVtbl->...`) 和 C++ 框架, 又难写又容易错.
- **规则**: 公开头文件纯 C (`extern "C"`; 异常不跨边界; 不出现 STL 类型; libwm 分配的内存用 `wm_free` 释放). 内部 C11 或 C++17 随意.
- **本机现实**: `runtime/llama` 里 b11429 的 `llama.dll` 是 MSVC 编的. 但 `llama.h` 是 C 接口, 本机现成的 MinGW gcc 13.2 就能直接链接它, 只缺同版本 (b11429) 的头文件.
  头文件版本必须完全一致, 因为有按值传递的结构体.

**libwm 怎么接进现有服务, 而且不改 wm 的代码**:
- wm 只用 llama-server 的 `/v1/chat/completions` 加几个扩展参数 (第 2 节). libwm 带一个兼容这个子集的本机 HTTP 端口, 对比时只改配置里的 `llm.endpoint`.
- 另一条路是在 wm 里加一个 ctypes 引擎, 那是 wm 的改动.

### 5.6 API 与 MCP

(M2a 已按这一节实现, 和计划不同的地方见第 6 节的"M2 进度".)

**OpenAI 兼容 API** (宿主提供, `127.0.0.1:8793`, 默认关, Bearer token):
- `GET /v1/models` 返回两个模型:
  - `wm-pet`: 回复由桌宠说出来, 带动作和表情;
  - `wm-text`: 只要文字, 页面另开一个不出声的连接.
- `POST /v1/chat/completions`:
  - `stream: true` 回 SSE 的 `chat.completion.chunk`, 否则一次返回.
  - 只取最后一条 user 消息当这一轮的输入; system 和历史消息忽略, 人设、历史、记忆都由服务端管 (文档写明).
  - 意图、情绪、置信度、`amend` 放在扩展字段 `wm` 里, 标准客户端会忽略.
- 第一版不支持 function calling、图片输入、`n > 1`、logprobs.
- 实现方式: 宿主不自己连 `/ws`, 通过 `chrome.webview.postMessage` 让页面转发. 所以宿主只需要一个 HTTP/SSE 库和一个 JSON 库.

**MCP 服务端** (宿主提供):
- **传输**: stdio 用 `wmpet.exe --mcp-stdio` (连到正在运行的宿主); Streamable HTTP 是 `http://127.0.0.1:8793/mcp`. 消息是 JSON-RPC 2.0.
- **版本**: 同时支持 2026-07-28 版和 2025-11-25 版, 现在很多客户端还停在后者.
  - 2026-07-28 版: 没有会话, 每个请求带元数据, 必须带 `MCP-Protocol-Version`、`Mcp-Method`、`Mcp-Name` 请求头.
  - 2025-11-25 版: 有 `initialize` 握手和 `Mcp-Session-Id`.
- **安全**:
  - 只绑 `127.0.0.1`. 校验 `Origin`, 不合法就回 403, 防 DNS 重绑定 (规范是 MUST).
  - Bearer token 首次启动时生成, 存在用户目录, 不进版本库.
  - 写操作按客户端名首次确认.

| 工具 | 作用 | 需要的改动 | 用户确认 |
|---|---|---|---|
| `pet_chat(text)` | 走完整一轮 (LLM + 记忆 + 回复侧检查), 返回回复和意图, 桌宠出声 | 无 | 否 |
| `pet_act(do, side?, amp?, spd?)` | 让桌宠做一个动作, 只限它声明过的技能 | 无 (页面本地执行) | 否 |
| `pet_state()` / `pet_show()` / `pet_hide()` | 显示状态、位置、门面、最近一句话; 显示或隐藏 | 无 | 否 |
| `pet_say(text)` | 说一句固定的话 (不过 LLM, 过回复侧检查) | wm 加上行 `say` | 每个客户端首次 |
| `memory_search(query, k)` | 检索长记忆, 返回条目和来源 | wm 加只读接口 | 每个客户端首次 (记忆是隐私) |
| `memory_add(text)` | 写一条记忆: 只追加, 打 `#mcp` 和客户端名, 走现有的去重和更正规则 | wm 加写接口 | 每次 (可选"总是允许这个客户端") |
| `memory_forget(id)` | 划掉一条 (沿用"划掉旧行", 不删除) | wm 加接口 | 每次 |

**MCP 客户端** (桌宠调用外部工具, M5):
- **白名单**: `desktop/config/mcp_servers.json` 是本机配置, 不进版本库.
- **权限分三级**, 每个服务器、每个工具各定一个:
  - 只读: 首次确认后自动调用;
  - 有副作用: 每次确认. 在气泡和托盘通知里给出"允许一次 / 总是允许 / 拒绝", 30 s 不回应算拒绝;
  - 禁用: 执行命令、删文件、付款、发消息, 一律不接.
- **什么时候调用**: 第一版只在用户明确说出指令时调用. 意图里加 `op: "tool"`, 置信度低于阈值时先问一句; 不让 0.8B 自主规划多步.
- **工具结果是数据, 不是指令**:
  - 结果包在 `[工具结果]` 块里给模型, 里面的"请你……"不执行.
  - 一轮最多一次工具调用, 结果不能再触发工具.
  - 记忆内容和对话历史不当参数发给外部工具, 除非用户确认这一次.
- **审计**: 每次调用记下服务器、工具、参数摘要、结果大小、用户的决定, 写进 `logs/mcp-*.jsonl`.
- **超时**: 10 s. 失败时角色说"没查到", 不编.

### 5.7 资源预算

| 状态 | 渲染 | 目标 |
|---|---|---|
| 隐藏 / 全屏游戏 / 暂停渲染 | 0 fps | 几乎不占 GPU; CPU 只剩每 2 s 一次全屏检测 |
| 空闲 (不说话、不动) | 15 fps, DPR <= 1.5 | 整机 CPU <= 1.5%, GPU <= 3% |
| 说话 / 做动作 | 30 fps | 和网页版同一套埋点, 延迟不退化 |
| 拖动 | 60 fps | 只在拖动期间 |

- **显存**: M0 实测渲染跑在核显上 (WebView2 用的是 Windows 默认显卡), 3060 的专用显存占用是 0, 不和 LLM、LoRA 训练抢.
  代价是贴图和缓冲放在核显共享的系统内存里 (见下一条). LLM 加嵌入约 2.6 GB 由服务端管, 桌宠第一版自己不加载任何模型.
- **内存**: 目标仍是宿主加 WebView2 进程组不超过 350 MB.
  M0 实测: 空页面约 210 MB; 加载 AvatarSample_B 后 1.0-1.3 GB, 其中 GPU 进程的核显共享内存 620-890 MB.
  M1 优化后约 360 MB, 主要靠压缩重复的变形纹理; 核显共享降到 114 MB. 见第 6 节"M1 进度".
- **单进程模式 (M4) 按需加载**:
  - 第一次唤起 (热键、点击、唤醒词) 时加载 LLM, 空闲 10 分钟后卸载 (可配置); 嵌入模型检索时才加载.
  - 冷启动时间要实测: 0.8B Q8_0 是 795 MB, 从 SSD 读入再上显卡, 估计 1-3 s. 冷启动期间先用待机动作和固定的"嗯?"顶上.
  - 显卡被别的进程占满时 (比如训练) 不上显卡, 退回 CPU 或提示.
- **测量**: 复用页面的 `FrameMeter` 和 `wm/resources.py`. 宿主自己的 CPU 和内存用 `GetProcessTimes`/PDH 读, 放进同一个资源面板.

**内存** (15 帧时):

| 情况 | 进程组私有内存 | 其中核显共享内存 |
|---|---|---|
| 空页面 (不加载角色) | 210 MB | 21 MB |
| 加载角色, 贴图不限 | 1016-1288 MB | 620-890 MB |

| 加载角色, 贴图限 512 (缩小 25 张, 画面看不出差别) | 971-1052 MB | 680-714 MB |

按进程拆开:
- GPU 进程 690-955 MB, 几乎全是核显共享内存;
- 渲染进程 165-230 MB, 浏览器进程约 69 MB, 其余 4 个小进程合计约 60 MB;
- 宿主 wmpet 8.6 MB (composition 宿主时 44 MB);
- 3060 的专用显存: 0.

**结论**:
- **可行**: 透明、点穿、`/pet/` 同源拦截、125% 缩放都可行.
- **选定 hwnd + layered**: 鼠标原生进页面, 不用转发. composition 留作备选.
- **达标情况**: CPU 大体达标 (空闲 15 帧 ≤ 1.5%). 核显 3D 4-7%, 没达到 3% 的目标. 内存 1.0-1.3 GB, 远超 350 MB 的目标.
- **超出的部分来自 VRM 渲染**, WebView2 本身只有 210 MB:
  - 贴图解码加 mipmap 约 158 MB, GPU 侧大约再翻一倍;
  - 脸部网格 8 个图元共用一份顶点缓冲, three.js 给每个图元各建一张 8.6 MB 的变形目标纹理 (57 个表情), 合计约 69 MB;
  - 剩下约 300-400 MB 还没查清.
- **先不走原生渲染 (M6)**, M1 里先做下面几项, 每项都用同一个自检量:
  - 合并或共享脸部的变形纹理;
  - 贴图压缩 (KTX2, 工具要另列下载);
  - 空闲时降到 10 帧, 像素比降到 1.0;
  - 看 MSAA 的开销.
- **渲染落在核显上是好事**: 不和阶段一抢 3060 的显存.

**没有自动验证的** (要人手试):
- 用真鼠标拖动和落地;
- 托盘菜单;
- 全屏程序时自动隐身;
- 光标轮询下实际的点穿手感;
- 多显示器和缩放变化 (DPI 切换).

### M1 进度 (2026-10-24): 内存降下来了, 连上了 /ws

**内存实验** (`desktop/scripts/memexp.ps1`). 条件: hwnd + layered, AvatarSample_B, 15 帧, 每项 10 s, 窗口 525×900. 单位 MB:

| 情形 | 进程组私有 | 核显共享 | GPU 进程 | 渲染进程 | 核显 3D |
|---|---|---|---|---|---|
| 基线 (贴图限 1024) | 1143 | 794 | 859 | 185 | 5.6% |
| 只加载、不渲染 (对照) | 405 | 54 | 108 | 198 | 0 |
| 变形纹理按图元压缩 | 628 | 292 | 360 | 169 | 5.9% |
| + 去掉变形法线 | 581 | 257 | 324 | 159 | 4.8% |
| + 上传后释放贴图原图 | 528 | 257 | 323 | 106 | 6.3% |
| + 贴图限 512 | 452 | 179 | 247 | 106 | 4.8% |
| 释放原图 + 内存目标"低" (贴图 1024) | 512 | 233 | 303 | 108 | 5.9% |
| 释放原图 + 关 MSAA + 像素比 1 (贴图 1024) | 504 | 233 | 299 | 105 | 4.0% |

- **大头是重复的变形纹理**: 只压缩这一项就省了约 515 MB, 远多于按文件估的 69 MB, GPU 侧有大幅放大.
  - 原因: 脸部 8 个图元共用一份顶点缓冲, three.js 按几何体建变形纹理, 每个图元都得到一张覆盖全部顶点的 Float32 纹理.
  - 做法: 每个图元只留自己索引用到的顶点. 网格对象不换, 表情绑定照常有效.
- **表情检查**: 把"张嘴 A"设成 0 和 1 各渲染一次, 脸部变化的像素数压缩前后都是 123, 表情没受影响.
- **关 MSAA + 像素比 1**: 核显 3D 降到 4%, 但头发边缘发糊、有锯齿和黑点, 不用.
- **默认组合**: 变形压缩 + 去变形法线 + 释放原图 + 贴图 512 + 内存目标"低". 窗口加高到 420×800, 顶部留气泡.

| 阶段 (默认组合, 窗口 525×1000) | 整机 CPU | 核显 3D | 进程组私有 | 核显共享 |
|---|---|---|---|---|
| 隐藏 | 0.20% | 0 | 386 MB | 152 MB |
| 暂停 | 0.16% | 0 | 365 MB | 133 MB |
| 空闲 15 帧 | 1.20% | 4.6% | **362 MB** | 114 MB |
| 30 帧 | 1.66% | 8.8% | 353 MB | 114 MB |

- **对比基线**: 内存从 1.1-1.3 GB 降到约 360 MB (-68%), 离 350 MB 的目标只差一点. 核显 3D 4.6%, 仍高于 3% 的目标.
- **测量修正**: 宿主自己的 CPU 现在是 0.02-0.08%. 之前读到 1.6%, 是 PDH 枚举 GPU 引擎计数器的开销落进了计时窗口, 已经改掉.

**连 /ws** (`desktop/web/talk.js`): 协议和网页一样, 服务端不用改.
- 处理的消息: 意图、情绪、回复、音频、A2F 面部、韵律、打断、打点.
- 头部动作交给 Soullink, 手势用程序动作, 不用 HAST-SEC.
- 能力声明里不报走动、看、转身、坐下、拿放.
- 头顶的气泡显示回复. 双击角色或托盘"说话…"打开输入框; 宿主把窗口设成前台, 让键盘进得来.
- 说话、做动作时页面升到 30 帧, 说完回到空闲帧率.
- 宿主设了 `--autoplay-policy=no-user-gesture-required`, 声音不用等用户先点页面.

**对话自检** (8792 的 mock 服务, 3 句):

| 说的话 | 意图 | 回复 | 说明 |
|---|---|---|---|
| 你好呀 | chat + 挥手 | 你好呀！今天想聊点什么？ | 口型幅度到 1, 收到韵律事件, 说话时 30 帧 |
| 先挥挥左手，再点点头 | act: 挥手、点头 | 好的，挥手、点头。 | 同上 |
| 走到窗户那边看看 | na (`body: ["go"]`) | 这个我还不会呢。 | 服务端按桌面能力声明改判 |

**卡住的工具调用** (2026-10-24):

- **服务端不等了** (`tool_cancel`): 原来只收起确认卡片, 在跑的停不下来; 现在走同一条路停掉 (不再回结果).
- **调用超时可配**: 面板里每个 MCP 服务器一个"调用超时" (`timeout_s`, 5 到 600 秒, 默认 60). 服务端等 90 秒, 设得更长的话服务端会先发 `tool_cancel`.
- 停掉和超时都按规范发 `notifications/cancelled` 告诉 MCP 服务器. 连接留着接着用: 超时、停掉不算断线, 不重连、只读工具也不重试 (原来超时也会重连重试, 一次最多等两个 60 秒).
- **顺带查出的退出卡死**: 本机接口的监听 socket 默认可继承, 宿主起 MCP 服务器子进程时被继承过去. 桌宠退出时 `closesocket` 之后 accept 不返回 (子进程还握着), 卡在停本机接口那一步, 作业对象也就一直不结束子进程. 改成 socket 不可继承, 起子进程时用 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` 只交 stdin、stdout、stderr. 退出时的日志加了"关闭窗口 / 页面已关 / 消息循环结束 / 本机接口已停"几步, 以后再卡能看出卡在哪.

**现状里和这件事有关的几点** (查代码确认的):
- 只有云端模型拿得到工具 (本地小模型不接). 所以工具读到的屏幕内容, 都会发给当前预设的那家云端.
- 服务端处理工具结果时只留文字 (`wm/cloud.py` 的 `result_text`), 图片块换成 `[image]` 占位. 现在截图根本到不了云端, 模型"看屏幕"只能靠界面元素的文字 (UI 自动化树、窗口标题).
- 服务端每轮最多调 4 次工具 (`llm.cloud.max_tool_calls`), 工具结果最多 8000 字 (`tool_result_chars`). 操作电脑一件事常要十几步 (看一眼、点、再看、打字…), 4 次不够; 整个桌面的元素树也常超过 8000 字. 要服务端改, 见下面"要服务端改的".
- 对话栏的"停"现在只停正在调的那一个 (`tool-stop`). 模型拿到"用户停掉了"之后, 还可能接着调下一个. 上行 `interrupt` 才会结束整轮, 没回的调用服务端会发 `tool_cancel` (`wm/pipeline.py` 的 `_run_tools`).

**权限设计**:

总的做法: 三道关, 都在桌宠宿主里.
1. 服务器的启动参数里就去掉危险的工具, 它们根本不存在.
2. 面板里每个工具的权限分四档, 加"锁定"和"这一轮都允许".
3. 守门: 每次动手之前, 宿主看目标窗口、目标 app. 碰到要你自己点的地方, 不问, 直接拦.

1. **四档**:

| 档 | 例子 | 默认 | 能改成 |
|---|---|---|---|
| 只读: 不读屏幕内容, 没副作用 | ControlStatus、DisplayInventory、Wait | 自动 | 都行 |
| 读屏: 屏幕上的文字或图会交给云端 | Screenshot、Snapshot、WaitFor; 手机的 State | 每次确认 | 每次确认 / 这一轮都允许 / 禁用. 不给"总是允许" |
| 动手: 点、打字、按键、拖、切窗口、开程序 | Click、Type、Scroll、Move、Shortcut、App; 手机的 Click、Type、Swipe、Press… | 每次确认 | 同上, 不给"总是允许" |
| 锁定: 能直接付款、发消息、删文件、改系统设置、执行任意命令、读隐私的 | PowerShell、FileSystem、Registry、Process、Clipboard、Scrape、Notification; 手机的 Shell、Notification、装卸 app、打开网址、设定位、剪贴板、云端设备、录屏、日志 | 禁用 | 确认卡片里放不开; 面板上显示一把锁, 改不了 |

   - 宿主怎么知道一个工具属于哪档: 认得的服务器 (Windows-MCP、Android-MCP、mobile-mcp) 内置一张表, 按工具名查. 面板里用"添加: 操控电脑 / 操控手机"按钮加的服务器带 `kind`, 照表走.
   - 不认得的服务器照现在的办法 (标了只读的自动, 其余每次确认). 标成"操控类"的服务器, 表里没有的工具一律按动手算.

2. **这一轮都允许**: 确认卡片多一个选项.
   - 只管这一轮 (服务端的 turn id)、同一个服务器的读屏和动手两档.
   - 你说下一句话、点了停、过了 5 分钟 (可配), 就作废.
   - 这样一件事从十几次确认变成一两次. 守门不受它影响, 照样拦.

3. **守门: 这些永远要你自己点** (拦下时不问, 直接回模型):

| 类别 | 拦什么 |
|---|---|
| 付款 | 支付宝、微信支付、云闪付、银行这类程序和窗口; 点的按钮名字是"支付""付款""确认付款""立即购买""提交订单""Pay""Buy now""Place order""Checkout" |
| 发消息 | QQ、TIM、微信、企业微信、钉钉、飞书、Telegram、Discord、Outlook、Foxmail 等聊天和邮件程序里一律不点、不打字、不读; 别的地方点"发送""发布""回复""评论""Send""Post""Reply"; 在这些程序里按回车 |
| 删文件 | FileSystem 已锁; 文件管理器里按 Delete、Shift+Delete; 点"删除""永久删除""清空回收站""Delete" |
| 改系统设置 | 设置 (SystemSettings.exe)、控制面板、注册表编辑器、组策略、任务管理器、Windows 安全中心、服务和设备管理器 (mmc.exe)、安装程序. UAC 弹窗本来就点不到 |
| 密码和登录 | 目标输入框是密码框 (UI 自动化的 IsPassword) 时不打字; KeePass、1Password、Bitwarden 和 Windows 的凭据弹窗不碰 |
| 同意条款、授权 | 点"同意""授权""允许""Accept""Allow""I agree" |
| 手机 | 每次动手前宿主用 adb 查前台 app (`dumpsys`): 微信、QQ、支付宝、云闪付、银行、设置、权限弹窗 (permissioncontroller)、安装器 (packageinstaller)、电话、短信、应用商店一律不碰; 锁屏时不打字 (不替你输解锁密码) |

   - 怎么查: Windows-MCP 的 Click、Type、Move、Scroll 参数里有屏幕坐标 (`loc`).
     - 宿主用 `WindowFromPoint` 找到窗口和程序, 再用 UI 自动化的 `ElementFromPoint` 读那一点的元素名字、是不是密码框. Shortcut 看前台窗口.
     - 按 Snapshot 编号点的, 从上一次 Snapshot 的结果里查坐标 (结果经过宿主); 查不到就当没把握, 这一次退回每次确认, 不吃"这一轮都允许".
     - 参数的具体名字装好后对一遍.
   - 名单放在设置里, 面板里能看、能加.
   - 拦下时: 回模型"这一步要用户自己来: 在「微信」里发消息", 对话栏也提示这一句. 她会说"这一步你来点哦"; 你点完说"好了", 她再接着做.
   - 局限 (要说清楚): 名单和按钮名字是尽力而为. 自己画界面的程序、游戏、网页里用图片做的按钮读不到名字; 检查和点击之间窗口也可能变 (很短). 所以守门是第二道关, 主要还是靠"动手要确认 + 看得见 + 一键停".

4. **截图和屏幕内容**:
   - **截图第一版不发云端**: 宿主把工具结果里的图片块拿掉, 只把文字交给服务端 (服务端现在也是占位, 两边都拦). 图片只在本机内存里, 不存盘; 对话栏里"她看了一眼屏幕"那一行可以点开看那张图 (可选).
   - **屏幕上的文字一样敏感**: 窗口标题、元素树、网页内容都会发给云端. 所以读屏一档每次确认, 卡片上写明"会把屏幕上的文字发给 DeepSeek"(当前预设的那家).
   - 聊天、付款、密码这几类程序不读 (见守门). 前台是它们时, 读屏也拦.
   - **以后**要让看得懂图的云端模型 (通义千问 VL、Kimi 的视觉模型) 看截图:
     - 每个预设一个开关, 默认关.
     - 打开后, 每张图发出去之前在卡片里先给你看缩略图, 你点"发"才发.
     - 要服务端改 (工具结果带图, 各家格式不一样). 第一版不做.
   - 审计日志照旧记参数 (打的字也在里面, 只在本机), 不记屏幕内容.

5. **一键停**:
   - **对话栏的"停"** (已有, 在 `host/src/tools.cpp` 的 `on_stop`): 操控类工具在跑时, 改成停整件事.
     - 先停掉正在调的那一个 (`tool-stop`);
     - 再发 `interrupt` 让服务端结束这一轮 (没回的调用它会发 `tool_cancel`);
     - 作废"这一轮都允许".
     - 不是操控类的工具, 停还是现在的样子.
   - **全局快捷键**: 宿主注册一个系统级快捷键, 桌宠不在前台、被盖住、在小屋里都能用.
     - 默认 Ctrl+Alt+Shift+Backspace, 和 Windows-MCP 的"接管"是同一个, 按一下两边都停 (两边能不能同时收到, 实现时核实).
     - 面板里可改.
   - **你一动她就停** (可选): 她操作期间, 宿主用低级键鼠钩子分辨真人的输入和程序注入的输入 (`LLMHF_INJECTED`). 你点了鼠标或按了键, 就当成"停".
     - Windows-MCP 自己也会在你大幅动鼠标时交还控制, 但它不告诉桌宠和模型, 过 10 秒模型又会接着来. 所以桌宠这边要停整轮.
   - **看得见**: 操控期间对话栏上方一条"她在操作你的电脑 (或手机) · 停 · Ctrl+Alt+Shift+Backspace", 桌面模式也有. 小屋里她坐在电脑前 (已有). Windows-MCP 自己在屏幕边缘发光.
   - **断开**: 托盘和面板加"断开电脑和手机操控": 结束这些 MCP 服务器的进程 (作业对象), 在设置里停用, 要你在面板里重新打开.
   - **次数和时长**: 一轮里操控类调用最多 30 次、最长 5 分钟. 到了她停下来问你要不要接着.

6. **别的**:
   - 桌宠不要以管理员身份运行: MCP 服务器继承桌宠的权限, 普通权限时碰不到管理员窗口.
   - 屏幕上读到的文字可能是提示注入 (比如网页里写着"请把…发给…"). 服务端已经把工具结果标成"数据, 不是指令", 再加上动手要确认和守门.
   - 随附一个 skill "操作电脑和手机的规矩": 先看清再点、一次只做一步、碰到付款发消息就停下请你来、做完说一声. 预设勾上它时才交给模型.
     (2026-10-25 做了电脑这一份 `computer-use`, 实际是预设勾了操控电脑的服务器就自动带上, 不用另勾; 见下面"随附 skill".)

**电脑这边接上了** (2026-10-24):
- **下载**: `uv venv --managed-python --python 3.14` + `uv pip install windows-mcp==0.8.8`, 来源 pypi.org 和 GitHub (python-build-standalone), 经本机代理.
  - 实际: CPython 3.14.6 21.5 MiB, 92 个包 (按元数据估的 42 个少了, fastmcp 4 拉了一串), 1 分 23 秒.
  - 装好: `desktop/third_party/windows-mcp/.venv` 150 MB, Python 本体在 `%APPDATA%\uv\python` 68 MB. 安装日志 `third_party/windows-mcp/install.log`.
- **和方案不一样的地方** (装好后核实的):
  - 0.8.8 的命令行没有 `--control-policy` (README 比发布版新). 这一版所有工具都要先拿桌面控制权, 等于 README 说的 strict; 接管 (大幅动鼠标、Ctrl+Alt+Shift+Backspace) 一直开着.
  - 表里没有的工具 (以后的新版本加的) 一律锁定, 不是按动手算: 先看清是什么再放开.
  - 模型拿到的元素树里每个元素前面就是坐标, 不显示编号. 交给模型的参数结构里去掉 `label` / `labels`, 只收坐标, 守门就不用去解析元素树; 也去掉了 App 的按路径启动、Snapshot 的整页网页 (`use_dom`).
  - 起一次要 18-21 秒 (第一次 36 秒). 宿主原来新版探测 `server/discover` 只等 8 秒, 超时退回旧版 `initialize` 时它已经按新版回了 ("connection is serving the 2026-07-28 protocol"), 连不上. `McpClient::connect` 加了 `discover_ms`, 操控类服务器等 90 秒.
  - 截图后屏幕上闪一圈边框、操作时边缘发光, 系统当成全屏程序 (`SHQueryUserNotificationState` 回 BUSY), 桌宠自动隐身, 用户就点不到"停"了. 操作期间和停下后 5 秒不因为全屏隐藏.

| C 核心和 Python 两份实现漂移 | libwm 只收低变动的部分; 规则表数据化后两边共用; 同一套基准当门槛 |
| WebView2 进程组内存达不到目标 (**M0 实测已出现**: 1.0-1.3 GB, 空页面只有 210 MB) | **M1 已降到约 360 MB** (变形纹理压缩、去变形法线、释放原图、贴图 512). 换别的模型要重测; 仍超出时再考虑贴图压缩 (KTX2) 或 M6 原生渲染 |
| 自检的对话写进真实服务的日志 (**M1 出过一次**) | 自检起的 mock 服务把 `trace.log_dir` 指到 `desktop/build/selftest/logs`; 混进去的 3 行已核对撤回, 有备份 |
| 显存不够 (训练时已用 5.9/6 GB) | 桌宠第一版不加模型; 单进程模式先查显存, 不够就不上显卡 |
| 游戏反作弊误判 (MateEngine 的教训) | 只用公开的窗口 API; 全屏或游戏时隐身, 并停止枚举窗口 |
| MCP 外部工具的提示注入、越权 | 白名单 + 权限分级 + 每次确认 + 工具结果当数据 + 审计 |
| 隐私: 前台程序、记忆通过 API 外泄 | 前台感知默认关, 只发类别; API 和 MCP 只绑本机并要 token; 记忆读写首次确认 |
| Live2D 发布许可 | 发布前问清; 在那之前 2D 只本机用 |
| 0.8B 的能力 (选工具、开放问答) | 只在明确指令时调用工具; 低置信度先问; LoRA 之后重新评估 |

## 10. 决策点

- **现在 (确认本文时)**:
  - 是否启动 M0: 要下载 WebView2 SDK (9.36 MB), webview/webview 可选.
  - Live2D 接入 (M1b) 做不做, 另行确认.
- **M0 结束** (2026-10-24 已定):
  - 宿主方式: HWND + 分层窗口, composition 留作备选. 直接写 COM, 没用 webview/webview (少下一样东西).
  - 资源: CPU 达标, 核显 3D 和内存没达标. 先在 M1 优化 VRM 渲染, 不进 M6.
- **M1 结束**: wm 要不要加 `state.place`、`state.desktop`、上行 `say` 这三项. 要加的话, 由阶段一的会话排期.
- **M2**: API 和 MCP 服务端放在宿主 (C++, 本文的建议) 还是 wm (Python). 如果记忆工具需要很多 wm 接口, 就改成 wm 里的可选模块, 默认关.
- **M3 开始前**:
  - 是否装 MSVC Build Tools.
  - libwm 怎么接 wm: 兼容 llama-server 的端口 (不改 wm, 建议) 还是 ctypes 引擎.
- **M3 结束**: libwm 的准确率或延迟达不到 llama-server, 就停在"桌宠 + Python 服务"的方案, 不做 M4.
- **M4 中**: 策略规则怎么进单进程模式. 三条路: 规则表数据化 + C 实现 / 内嵌 Python / 一直要求装 Python 服务.
- **发布前**: 向 Live2D 确认可扩展应用; 选定默认角色; 去掉 HAST-SEC; 核实 TTS 数据的许可.
- **外接大模型 API** (像《妹居物语》那样玩家自己配 API): 做不做; 做的话, 记忆内容要发到云端, 用户确认怎么设计.
- **玩电脑 (操控电脑、手机)**: 用哪个 MCP 服务器、截图发不发云端、守门名单, 见 6 节"玩电脑 = 远程操控电脑和手机"末尾的五个问题.
- **扩展中心 (插件、社区、函数调用、MCP)** (2026-10-25, 学 AstrBot): 社区索引放哪、第一批内置工具、只收 MCP 插件还是也收 Python 插件、谁来审上架, 见 [extensions.md](extensions.md) 第 8 节.
