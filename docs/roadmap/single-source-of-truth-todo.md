# 待办与「日程事实」的单一真相源（方案 v0.1，2026-11-19）

第七切片（第三个插件 + 真相源）配套方案。结论先行：**不是让两处互相同步，而是把两条链切开、各自只当一段真相的持有人**；插件只写自己的账，记忆只写"用户说过什么安排"，谁都不复制谁。

## 一、谁说了算（责任边界）

| 问题 | 真相在哪 | 谁写 | 谁能读 |
| --- | --- | --- | --- |
| 我最近有什么安排 / 计划 | 记忆：`记忆/关于用户.md` 里带日期的 `#auto-memory` 事实行 | 记忆的 `observe`（`wm/memory.py:1537`）：规则 `extract_facts` 从用户原话提取、`settle_fact` 落日期后 `_append` | 宿主主进程 `Memory._list_facts`（`wm/memory.py:1443`） |
| 某条待办做没做完 / 撤没撤销 | 待办插件：`~/.worldmodel/plugins/todolist/todos.jsonl` 的 `done_at` | 插件动作 `todo_done` / `todo_undo`（只改 `done_at`，不删行） | 插件自己；宿主核对读同一文件 |
| 这条待办当初从哪句话来的 | 插件 `source` 字段，存用户原话（≤200 字） | `todo_add(source=...)` | 插件；人看工作台时当线索 |

一句话：**"安排了什么"归记忆，"办没办"归插件。** 记忆里不存在完成状态，插件里不重写安排事实，所以大多数"冲突"在这套切分下根本不会发生。

## 二、两处现在各自怎么长出来的（读代码得到的现状）

- 记忆侧：`wm/memory.py:1443-1498` 的 `_list_facts`，类别来自 `wm/memory_graph.py:119` 的 `list_query`；命中「日程」后用窗口规则刷选 chunk——「这周/本周」→ 7 天、「这个月/本月」→ 31 天、「安排/计划/待办/要办/下次/接下来」→ 今天起 120 天（只列没到的）、「最近/近期」→ ±30 天；正文必须不以「用户」开头、跳过日志与重复原文；日期由 `wm/memory_ops.py:102` 的 `event_date` 从原话解析，解析不出就跳过；**最多 4 条**，服务端直接答（不走模型）。
- 插件侧：`plugins/todolist/plugin.py`，`WM_TODO_HOME` 可覆盖数据目录；`todos.jsonl` 一行一条、追加写；`done`/`undo` 时才整份重写（临时文件 + `os.replace`），坏行原样保留并计入 `skipped_lines`；每次 act 回读核对 `verified`，回执进 `receipts.jsonl`。
- 记忆的候选通道已存在但**不参与检索**：`Memory.propose`（`wm/memory.py:2071`）写 `记忆/候选.md`，`Memory.propose_said`（`:2112`）收私聊原话，`Memory.candidates`（`:2153`）只供展示；只有确认后才进 `关于用户.md`。所以"插件把待办写进候选"不是加一行调用那么简单。

## 三、同步方案（本切片的最小实现）

**不做双向同步。** 本切片只做三件最小事：

1. `todo_add` 收一个可选 `source`（用户原话 ≤200 字），把两边能对上的线索留下来；它只是文字，不解析、不校验、不回写记忆。
2. 插件不读记忆文件、不调 `Memory` 的任何方法。原因是进程隔离：插件跑在 `plugin_worker` 子进程里（`wm/agent/plugin_host.py` 的 `_run_entry`），拿到的是空白的 Python 进程，`Memory` 活在 app 进程；宿主 `plugin_host` 模块本身也没有 `hub` 引用。
3. 口径统一写在两边各自的返回里：插件返回 `reason` 只谈待办条数与完成情况，不宣称"你记忆里有这条"；记忆的回答保持"你说过 / 安排在什么日期"，不带完成状态。

**依赖（做不了的部分，写清楚不硬做）**：若以后要"插件写入也进记忆候选"，需要宿主在 `invoke` 成功后回调 `Memory.propose` / `propose_said`（`wm/memory.py:2071`、`:2112`，不在本切片的禁改清单里，但要把 `hub` 传到 `plugin_host` 层——`wm/agent/studio.py` 分派处有 `hub.studio`，可加一个只读回调）。本切片不改，理由：这会把插件宿主的调用链和记忆写入耦在一起，先观测一段时间再动。

## 四、冲突怎么判（按优先级）

1. **完成状态冲突不存在**：只有插件有 `done_at`，记忆没有这个字段；`todo_done`/`todo_undo` 幂等，重复调用不产生第二行回执、也不改 `done_at`。
2. **内容/日期不一致**：以记忆的事实行为准（它是从用户原话提取并 settle 过日期的）；插件的 `source` 是原话副本，只当线索，不当真相。
3. **同一件事同时有事实和待办**：两处各显示各的，**不自动合并**；要合并必须先有人确认（本切片不做自动合并）。
4. **插件文件坏了/被手改**：坏行原样保留并计入 `skipped_lines`；`done`/`undo` 对坏行不炸；记忆侧完全不受影响。
5. **插件谎报**（说写了、文件里没有）：插件自己的 `verified` 与宿主独立核对（`WM_PLUGIN_HOST_VERIFY=on` 时写审计 `host_verified`）都会留下痕迹；不一致时宿主只加 `warnings` + `E_VERIFY_DISAGREE` 审计，不直接判失败（先观测）。

## 五、给用户看的两处口径

- 记忆/问答侧：「你最近安排了：…（<日期>）」——只说安排，不带"做没做"。
- 工作台插件卡片/插件列表侧：「待办 N 条（没做完 M 条）」+ 最近几次调用成功没有——只说进度，不解读日期。
- 两边要讲同一件事时，用一句话连起来：「你安排过 X（记忆），待办里这条还没打勾（插件）」。**不把两边的数字加在一起**（会重复计数）。

## 六、明确不做（以及为什么）

- 不双向同步：两边写权限不同（记忆只由对话写入，插件在子进程），同步等于给插件开一条改记忆的路，风险大于收益。
- 不把待办写进记忆、不让插件读记忆文件：隐私与进程边界。
- 不解析 `due` 成时间、不做到期提醒：那会变成第二个时间真相源，直接和 `event_date` 打架。
- 不自动合并重复：合并需要"确认"这个人类动作，未实现前宁可见两条。
