# 首包拆解（v5turbo，2026-11-20）

> 一句话：v5turbo 的「首包」不是 1.3 s 那一档了 —— 它是**非流式**，第一个字节要等整句合成完；实测生产里 `首包 ≈ 1.45 s + 0.6 × 音频时长`，另有约 **+1.0 s 是和本机 llama 抢同一张 6 GB 卡**的账。

## 1. 结论

1. **v5turbo 没有"可再拆的 1.3 s 固定成本"**：它不在流式路径上，`首次出字节 = 整句合成结束`。2 个字符最短也要 1.45 s（音频才 0.28 s），17 个字符 3.55 s。
2. **分段实测（GPU 空闲、进程内计时）**：文本 G2P+BERT 0.13 s ／ GPT 出语义 token 0.88–1.30 s ／ 参考音 + 目标句的 `decode_encp` 0.26–0.47 s ／ v5 mel（cfm 4 步）0.25 s ／ vocoder 0.42–0.52 s，合计 1.94–2.79 s。
3. **同卡争用是第二笔大账**：把 8784（本机 0.8B llama）停掉，同一批句子首包从 2.84 / 3.25 / 4.07 s 掉到 **1.93 / 2.34 / 3.04 s**（省 0.9–1.0 s）。停 llama 后 GPU 常驻从 4662 → 3458 MiB。
4. **首句越短越快，这是现在唯一还能立刻用的杠杆**：`pipeline.first_clause_min_chars = 4`，首句通常 4–10 字 → 首包 1.4–2.4 s；同一句话如果整句丢给 TTS（17 字）就是 3.5 s。
5. 试过**参考音侧缓存**（`fea_ref/ge` + 参考音重采样 + 参考梅尔谱只算一次）：理论省 ~0.13 s，实测落在噪声里（1.44 → 1.42，±0.1），已**回滚**，不留这个改动。

## 3. 分段：钱花在哪

进程内计时（先停 9880 腾出整张卡，只剩 TTS 自己；`ttfb` 是该句总时间）：

| 句 | 音频 | 总(首包) | 文本 G2P+BERT | GPT 语义 token | decode_encp(参考+目标) | v5 mel 4 步 | vocoder |
|---|---|---|---|---|---|---|---|
| 外面下雨了，记得带伞。(11字) | 2.40 s | 1.81 s | 0.14 | **0.88** | 0.26 | 0.25 | 0.42 |
| 你要是累了就先歇一会儿，我不催你。(17字) | 3.44 s | 2.53 s | 0.13 | **1.30** | 0.47 | 0.25 | 0.52 |
| 嗯。(2字) | 0.28 s | 1.09 s | 0.21 | ~0.3 | 0.26 | 0.27 | 0.29 |

- **GPT（AR）那一段随字数线性涨**，是唯一"字多就慢"的部分。
- **v5 mel 0.25 s、vocoder 0.42–0.52 s 基本是常数**：cfm 要把参考音（约 200 帧）+ 目标帧一起跑 4 步，参考音那段长度固定，所以短句也在付这笔钱。
- `decode_encp` 两次（参考音一次、目标句一次），参考音那一次本来可以缓存，但实测省不出时间（见结论 5）。

## 4. 长度实验：固定 1.4 s + 0.6×音频时长

生产链路（HTTP 直打、每句 3 次取中位、`seed 42`、实例已预热）：

| 文本 | 字数 | 音频 | 首包（3 次） | 中位 |
|---|---|---|---|---|
| 嗯。 | 2 | 0.28 s | 1.45 / 1.54 / 1.39 | **1.45** |
| 我在呢，你回来啦。 | 9 | 2.56 s | 3.74 / 2.71 / 2.93 | **2.93** |
| 你要是累了就先歇一会儿，我不催你。 | 17 | 3.44 s | 4.71 / 3.52 / 3.55 | **3.55** |

→ `首包 ≈ 1.4 s（固定）+ 0.6 × 音频时长`。
误差主要来自同卡争用和 GPU 时钟（实测空闲 352 MHz、跑起来 2032–2077 MHz）。

## 5. 争用实验：llama 在同卡上要多付 1 s

同一批三句，先测"有 llama"，再 `python -m wm.services stop llm`（8784 关、GPU 4662 → 3458 MiB）后立刻再测，最后 `restart llm` 恢复：

| 句 | 有 llama | 只有 TTS | 差 |
|---|---|---|---|
| 嗯，我在。 | 2.84 s | **1.93 s** | −0.91 |
| 外面下雨了，记得带伞。 | 3.25 s | **2.34 s** | −0.91 |
| 你要是累了就先歇一会儿，我不催你。 | 4.07 s | **3.04 s** | −1.03 |

llama 空闲时不占算力，但它的权重 + KV（`ctx 16384`）+ CUDA 上下文约 1.2 GB；这张卡剩给 TTS 的余量只有 ~1.4 GB，而 TTS 峰值要 ~1.3 GB —— 分配器一紧，`cudaMalloc`/同步就变慢。

## 6. 试过但没用 / 不建议

- **参考音侧缓存**（`using_vocoder_synthesis` 里 `fea_ref/ge/mel2` 只算一次）：实测 1.44 → 1.42，噪声内，**已回滚**（`runtime\gpt-sovits\GPT_SoVITS\TTS_infer_pack\TTS.py` 现在是原版）。
- **降 `sample_steps`**：v5turbo 已经是 4 步（上游蒸馏版），再降到 2 步没有人验证过质量，而且 mel 段只占 0.25 s，省不出多少。
- **给 v5 开 CUDA graph**：就是之前查出来的哑音根因（`operation not permitted when stream is capturing`），不能开。
- **把 llama ctx 从 16384 压小**：`--parallel 4`、每槽 4k，注释写明提示词约 2.9k token，压到 12288 每槽只剩 3k，风险大于收益。
- **让 llama 挪到 CPU**：首 token 会从 30–120 ms 变成秒级，得不偿失。

## 7. 还能继续压的三条路（按性价比）

1. **让首句更短就开口**：`first_clause_min_chars` 现在 4，已经是这套写法里最激进的；真正能再快的是"先出一声「嗯」"这类语气垫片（v5 有 12 token 静音下限，太短的句子会哑，2 字是安全下限）。收益 ~1.0–1.5 s，代价是要改回复生成策略。
2. **把 llama 的常驻挪开或压小**（-0.9 s）：例如聊天时按需起 8784、空闲就停；或者换成更小的量化 + 更小 ctx。收益明确但会牺牲首 token。（**这条后来被证伪，见 9.3：空闲的 llama 不拖慢 TTS**。）
3. **混合**：短语气句走 v2ProPlus 流式（首包 1.0–1.4 s、音色旧）、正式长句走 v5turbo。代价是两句音色不一致，用户盲听时能听出来。

### 9.2 为什么以前关掉了，现在怎么防

- 11-19 用 **v5dev + satio LoRA** 试过：捕获在 `Accel/PyTorch/AR/t2s_model_abc.py:317` 抛 `RuntimeError: CUDA error: operation not permitted when stream is capturing`。一次失败 = 一句 **0.33 s 纯静音**（`TTS.py:1680` 的 except 分支 `yield 16000, np.zeros(int(16000))`）+ `del self.t2s_model` 后重载失败 → 之后所有请求 400 `'TTS' object has no attribute 't2s_model'`。所以当时直接 `CUDAGraph=0` 关掉，代价就是首包多 0.9–1.2 s。
- 这次 v5turbo + `--base`（`s1v3.ckpt` + `s2Gv5turbo.pth`）**捕获成功**（日志 `flash_attn_varlen_cuda_graph Backend`，`0/1` 进度条那两句就是捕获），所以默认只给 v5turbo 打开；v5dev 仍默认关闭。
- 兜底（`tools/start_tts.py`）：预热后看返回音频字节数，`< 60000`（48 kHz 下 0.6 s）就判为「像是捕获失败」，**杀掉子进程、用 `CUDAGraph=0` 重起一次**再预热。`WM_V5_GRAPH=0/1` 可强制关/开。
- `TTS.py` 里只留了一处改动：`_v5_ref_side()` 缓存参考音那一侧（`fea_ref/ge/mel2`，本来每次请求都重算），以及 `using_vocoder_synthesis` 走这个缓存。**调试用的 token dump / print 已删干净**。改前原版：`TTS.py.orig-20261120-v5stream`。

### 9.3 试过但没用/不做的（免得后来的人再走一遍）

| 方案 | 结果 |
|---|---|
| 烤机提频（全占 SM 的 matmul 循环） | **反效果**：ttfb 2.5 → 16–30 s，抢 SM 远大于提频收益 |
| 轻占空比保频（2 ms / 300 ms） | 无用，时钟仍 210 MHz；10 ms/90 ms 版还会让 ttfb 慢 0.3–0.5 s |
| 先占 1.1 GB 显存再测 | 与「llama 在卡上」同显存占用时 ttfb 不变 → **显存压力不是原因** |
| `nvidia-smi -lgc` 锁频 | 需要管理员，本机没权限 |
| 关掉 llama | 空闲的 llama 不拖慢 TTS（1.90/2.46/3.23 vs 1.92/2.53/3.06）→ 第 7 节「llama 争用 0.9–1.0 s」**这条结论作废** |
| 参考音侧缓存 | 关图时无收益（那 0.4 s 不是瓶颈）；开图后保留，没有副作用 |
| 按语义 token 分块合成（真流式原型） | 短句 ASR 正常；**长句按比例切 phone 会糊**（「你先歇一会儿」→「你要去拜好这先睡会儿」），根因是 token↔phone 没有真实对齐、停顿吃 token。**暂不做**，现在也不需要 |
